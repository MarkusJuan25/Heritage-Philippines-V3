## D-011 — Authentication library selection

- **Status:** Accepted
- **Date accepted:** July 10, 2026
- **Decision:** Better Auth, with its official Prisma/PostgreSQL adapter (`better-auth/adapters/prisma`), is the authentication and session library for Heritage Philippines V3. This fulfills ADR-001's deferred "Select a vetted authentication/security library after checking its official documentation" follow-up action (ADR-001, "Immediate, pre-Phase-1-scaffolding").
- **Rationale:** Evaluated against Lucia and Auth.js (NextAuth). Lucia was deprecated by its maintainer in March 2025 and is no longer distributed as an installable library (repositioned as an educational resource) — disqualified as "maintained." Auth.js's Credentials provider is architecturally hardcoded to JWT-only sessions and cannot use real database-backed sessions without unsupported workarounds, conflicting with ADR-001's stated preference for "database-backed session state" and this project's rule against inventing custom session mechanics. Better Auth supports credentials-based login and database-backed sessions natively through its official Prisma adapter, hashes passwords internally (scrypt) rather than requiring custom cryptography, and supports disabling public self-service sign-up (`emailAndPassword.disableSignUp`) while keeping sign-in enabled — required to satisfy blueprint Section 7's invitation-only-signup rule. As of September 2025 the Auth.js/NextAuth maintainers themselves joined the Better Auth project and now recommend it for new projects. It requires no serverless-specific hosting platform, remaining compatible with Hostinger-managed VPS-class Node.js hosting (ADR-001).
- **Constraint:** This selects a library within ADR-001's already-approved architecture (Next.js, Prisma, PostgreSQL, cookie-based sessions) and does not alter the accepted technology stack. It does not implement custom cryptography, password hashing, or session-token primitives, consistent with ADR-001's security requirements.
- **Effect:** Implements the technology choice underlying the Phase 1 "Establish authentication/session foundation" checklist item in `docs/HERITAGE_V3_TASK_BOARD.md`. Final MFA/SSO and any additional auth providers remain open per blueprint Section 16.2.

## D-012 — Better Auth admin plugin evaluated and rejected for staff management

- **Status:** Accepted
- **Date accepted:** July 13, 2026
- **Decision:** The installed Better Auth admin plugin (`better-auth@1.6.23`, `better-auth/plugins/admin`) was evaluated as a candidate implementation for the Phase 1 "staff account, role, and assignment management" checklist item and rejected. Heritage Philippines V3 will instead implement a custom, audited staff-management service (Approach B) built on the project's existing Prisma client, role guards (`src/lib/auth/roles.ts`, `authorize.ts`, `guards.ts`), and only the non-plugin Better Auth server primitives already in use (e.g., `hashPassword` from `better-auth/crypto`, as `prisma/seed.ts` already does). The `admin` plugin must not be registered in `src/lib/auth/auth.ts`, and no `/api/auth/admin/*` route may exist.
- **Rationale:** Direct inspection of the installed package's compiled source (`dist/plugins/admin/{admin,routes,schema,types,has-permission}.mjs`) found three conflicts with Heritage's requirements: (1) the plugin's endpoints (`set-role`, `create-user`, `ban-user`, `remove-user`, etc.) are unconditionally mounted on the same catch-all handler this project's `/api/auth/[...all]` route already forwards everything to — there is no supported way to use the plugin's server APIs internally without also exposing those endpoints over HTTP, authorized only by the plugin's own parallel `adminRoles`/`ac` permission config rather than this project's fixed six-role model; (2) the plugin redefines `user.role` as an unconstrained string (`type: "string"`, not required), a different shape from this project's own six-value literal-union `role` field, and its `setRole` endpoint has no self-action or "last remaining admin" protection; (3) its mutation endpoints call Better Auth's internal adapter directly with no exposed transaction hook, so an `AuditLog` write can never be atomic with the mutation it records, and `removeUser` is a hard delete rather than the deactivate/reactivate model the blueprint calls for.
- **Constraint:** Heritage retains its fixed, blueprint-approved six-role `Role` enum and keeps permissions expressed in code rather than adopting the plugin's own role/permission system. The staff-management service (implemented in a later checkpoint) must perform staff account creation, role changes, and deactivation/reactivation as direct, atomic Prisma operations (mutation + `AuditLog` insert in one transaction), not through any Better Auth admin-plugin endpoint.
- **Effect:** Closes the Approach A vs. B vs. C evaluation for this checklist item in favor of Approach B. Direct credential provisioning (a System Administrator setting a new staff account's initial password) must be covered by an integration test in the staff-management-service checkpoint that verifies the created account can actually authenticate through the normal Better Auth sign-in path — not merely that a database row was written correctly.
- **Implementation status update (July 21, 2026):** The staff-management service and its four `SYSTEM_ADMINISTRATOR`-only API routes are implemented and unit-tested. The integration requirement in D-012 is satisfied by `apps/web/src/features/staff/service.integration.test.ts`: all three tests passed against the disposable local PostgreSQL database `heritage_v3_test` using the real `createStaffAccount`, `deactivateStaffAccount`, and Better Auth `auth.api.signInEmail` paths. This verifies sign-in using both generated and caller-supplied passwords, plus sign-in rejection and session revocation after deactivation. `heritage_v3_dev` was not used; staging and production remain unverified.

## D-013 — Server-generated booking reference format

- **Status:** Accepted
- **Date accepted:** July 16, 2026
- **Decision:** `Booking.bookingReference` (blueprint Section 13.4) is generated exclusively by the server as the literal prefix `HPB-` followed by 20 uppercase hexadecimal characters (e.g. `HPB-7A31F09C45D2E86B104F`), derived from 10 cryptographically secure random bytes via Node's built-in `crypto.randomBytes` — no new dependency is introduced. It is never supplied or overridable by a client: `POST /api/bookings`'s request schema (`apps/web/src/features/bookings/schemas.ts`) has no `bookingReference` field at all, and the service layer (`apps/web/src/features/bookings/service.ts`'s `generateBookingReference`) is the only place this value is produced.
- **Rationale:** Blueprint Section 13.4 names "Booking reference" as a Booking field but specifies no format, sequence, or generation rule anywhere in the blueprint, this decisions log, or the task board — this was an explicitly open item identified during the Booking Schema Foundation checkpoint's implementation reconnaissance. A random, non-sequential, non-year-based identifier avoids leaking booking volume or timing through the reference itself and avoids the coordination cost a sequential counter would require under concurrent creation. `Booking.bookingReference`'s existing database `@unique` constraint (migration `20260716020734_booking_schema_foundation`) remains the final safeguard regardless of generation method; the booking-creation service additionally retries with a freshly generated reference, within a small bounded retry policy, on the rare event of a collision.
- **Constraint:** Sequential or human-readable (e.g., year-prefixed, incrementing) booking references are deferred unless management later requires them — this decision does not preclude revisiting the format, but any change must go through this same decision process, not be introduced ad hoc in a later checkpoint.
- **Effect:** Resolves the previously open "booking reference generation" item identified during the Booking Schema Foundation checkpoint. Implemented as part of the booking workflow enforcement checkpoint (explicit Booking creation, staff-only list/read, initial `BookingStatusHistory`, and the `BOOKING_CREATED` audit entry) — status-transition enforcement and Booking-specific staff-assignment endpoints remain separate, not-yet-implemented checkpoints.

## D-014 — Booking status-transition matrix, authorization, and concurrency

- **Status:** Accepted
- **Date accepted:** July 16, 2026
- **Decision:** `PUT /api/bookings/[id]/status` enforces the following fixed, service-layer transition matrix over `BookingStatus` (blueprint Section 13.4's ten values), independent of any database constraint:
  - `DRAFT` → `PENDING_CONFIRMATION`, `CANCELLED`
  - `PENDING_CONFIRMATION` → `CONFIRMED`, `CANCELLED`
  - `CONFIRMED` → `IN_PREPARATION`, `CANCELLED`
  - `IN_PREPARATION` → `DOCUMENTS_REQUIRED`, `VISA_PROCESSING`, `READY_FOR_TRAVEL`, `CANCELLED`
  - `DOCUMENTS_REQUIRED` → `VISA_PROCESSING`, `READY_FOR_TRAVEL`, `CANCELLED`
  - `VISA_PROCESSING` → `DOCUMENTS_REQUIRED`, `READY_FOR_TRAVEL`, `CANCELLED`
  - `READY_FOR_TRAVEL` → `IN_PROGRESS`, `CANCELLED`
  - `IN_PROGRESS` → `COMPLETED`, `CANCELLED`
  - `COMPLETED` → no outgoing transitions (terminal)
  - `CANCELLED` → no outgoing transitions (terminal)

  Authorization mirrors Booking creation/read exactly: `ADMIN_MANAGER` (unconditional) and `TRAVEL_CONSULTANT` (only through the existing active-Client-assignment check, `features/bookings/repository.ts`'s `clientAssignmentFilter` — not a new Booking-specific assignment mechanism, which remains unimplemented). `SYSTEM_ADMINISTRATOR`, `FINANCE_ACCOUNTING`, `VISA_DOCUMENTATION`, and `CLIENT` are not authorized to change Booking status in this checkpoint.

  Concurrency: the caller supplies `expectedStatus` alongside `newStatus`; the service reads the Booking's actual current status inside a `runSerializableWithRetry` transaction and rejects with `BOOKING_CONFLICT` (409, refresh-and-retry message) if the current status no longer matches `expectedStatus` — an optimistic-concurrency check layered on top of (not a replacement for) the transaction's own serializable-conflict retry. A request whose `newStatus` already equals the current status is a no-op (no history row, no audit entry, no write) — required by `booking_status_history_status_changed`'s existing CHECK constraint, which forbids a history row where `previousStatus` equals `newStatus`.

  `DOCUMENTS_REQUIRED` and `VISA_PROCESSING` are treated as coarse overall booking-stage indicators only, not as a model of the detailed, genuinely parallel document/visa workflows blueprint Section 8 describes ("payments, documents, visa processing... may all progress in parallel rather than strictly in sequence"). `Booking.status` remains a single scalar reflecting the booking's overall stage; the future `Document` and `VisaCase` entities (blueprint Sections 14.7, 14.8) own their own detailed, independently-progressing status fields once implemented. No schema change accompanies this decision.
- **Rationale:** Blueprint Section 13.4 lists the ten status values but defines no transition graph or role authority over them, and Section 8 explicitly warns that the underlying workflows are parallel, not sequential — modeling that fully would require the not-yet-implemented `Document`/`VisaCase` entities, which is out of scope for this checkpoint. The matrix above is a deliberately conservative starting point (forward progression plus universal cancellation from any non-terminal state, since no blueprint text restricts when cancellation is allowed) rather than an attempt to fully resolve the parallel-workflow tension now. Reusing active-Client-assignment (rather than introducing Booking-specific `StaffAssignment` targets, which the schema supports but no service/route yet populates) keeps this checkpoint additive and avoids authorizing against an assignment type nothing can currently create.
- **Constraint:** This matrix, and the two-role authorization set, may be revised by a later decision once `Document`/`VisaCase` are implemented and the parallel-workflow question is revisited; until then, no additional role or transition should be added ad hoc outside this decision. A `reason` field for status changes is explicitly deferred, not adopted, in this checkpoint.
- **Effect:** Implements the "Booking status-transition enforcement" checkpoint referenced in `docs/HERITAGE_V3_TASK_BOARD.md`. Booking-specific staff-assignment management and any Document/VisaCase-driven status model remain separate, not-yet-implemented checkpoints.

## D-015 — Booking-specific staff-assignment enforcement

- **Status:** Accepted
- **Date accepted:** July 16, 2026
- **Decision:** `PUT /api/bookings/[id]/assignment` lets an Admin / Manager set or replace the Travel Consultant assignment for a specific Booking, extending the existing `features/assignments` shared implementation (`TargetKind` now includes `'BOOKING'` alongside `'LEAD'`/`'CLIENT'`) rather than introducing a separate Booking-assignment service. Booking assignment is **independent of the underlying Client assignment**: the assignee is never required to already hold the Booking's Client's active assignment, and no cascade exists in either direction — ending, replacing, or creating a Client assignment never touches an existing Booking assignment, and vice versa. This checkpoint **does not affect** Booking read, list, or status-transition authorization: `features/bookings/repository.ts`'s `clientAssignmentFilter` and the D-014 status-transition authorization rules are unchanged and continue to gate Travel Consultant access via active Client assignment only. This checkpoint is **`PUT`-only** — no `DELETE`/removal-without-replacement endpoint exists for Booking assignment; ending a Booking assignment without an immediate replacement is deferred, not decided against permanently.
- **Rationale:** Blueprint Section 4.2 explicitly grants Admin / Manager the capability to "manage staff accounts' operational role assignments and lead/client/booking assignments," naming Booking directly — the same explicit basis Lead and Client assignment already rely on. The underlying `StaffAssignment.bookingId` column, its three-way `leadId`/`clientId`/`bookingId` XOR CHECK constraint, and its partial unique active-Booking-assignment index were already added by the Booking Schema Foundation checkpoint (migration `20260716020734_booking_schema_foundation`) but never used by any service or route until now — extending the existing generic `setAssignment`/`endAssignment` control flow (idempotent same-assignee replay, `REASON_REQUIRED` only when replacing an active assignment, atomic end-old/create-new/audit inside `runSerializableWithRetry`) maximizes reuse of already-reviewed, already-tested logic rather than duplicating it. Leaving Booking read/status authorization on Client-level assignment avoids conflating two separate concerns — "who currently works this Booking" (new, additive) and "who may read or transition this Booking" (existing, unchanged) — until a future decision, if any, deliberately links them.
- **Constraint:** Whether a Booking assignment must eventually require, or should remain independent of, the Client assignment; whether Booking read/status authorization should ever incorporate Booking-level assignment; and whether assignment removal without replacement should be added, are all left open for a future decision — none is silently resolved here. No Prisma schema or migration change was required or made for this checkpoint.
- **Effect:** Implements the "Booking-specific staff-assignment enforcement" checkpoint referenced in `docs/HERITAGE_V3_TASK_BOARD.md`. `features/bookings/repository.ts`, its status-transition service, and their routes remain completely unchanged.

## D-016 — Conversation Schema Foundation: schema shape, read-state model, and migration-history remediation

- **Status:** Accepted
- **Date accepted:** July 17, 2026
- **Decision:** The Conversation Schema Foundation schema-only checkpoint (blueprint Sections 4.2–4.6, 9.1, 10, 10.1, 10.2, 10.3, 13.9, 14.3) adds `ConversationCategory` (the eight closed categories in Section 10.2, adopted directly), `MessageVisibility` (`CLIENT_VISIBLE`/`INTERNAL_NOTE`, Section 10.1), `ConversationParticipantRole` (`CLIENT`/`TRAVEL_CONSULTANT`/`FINANCE_ACCOUNTING`/`VISA_DOCUMENTATION` — deliberately excluding `ADMIN_MANAGER`, since Section 10.1 treats Admin/Manager's full visibility as a role-wide grant, not thread participation), `Conversation`, `ConversationParticipant`, `Message`, and `MessageAttachment`. Key shape decisions:
  - `Conversation.clientId` is a required direct FK to `Client` (mirroring `Lead`/`Proposal`/`Booking`), since a Conversation may have no related Booking or Proposal at all.
  - A Conversation may reference **at most one** related record in this checkpoint — an optional `relatedBookingId` or an optional `relatedProposalId`, never both (enforced by CHECK, see below). A `relatedVisaCaseId` is not modeled: VisaCase does not exist anywhere in this schema yet, matching its existing deferral as a `StaffAssignment` target.
  - `ConversationParticipant` uses two mutually exclusive identity paths — `staffUserId` (User) for `TRAVEL_CONSULTANT`/`FINANCE_ACCOUNTING`/`VISA_DOCUMENTATION` and `clientProfileId` (ClientProfile) for `CLIENT` — tied together by one CHECK constraint per participant row. `joinedAt`/`removedAt` preserve membership history (mirroring `StaffAssignment.endedAt`) rather than deleting a row on removal, and a person may rejoin after removal.
  - Read state (Section 10.1's "read status") is modeled as **`ConversationParticipant.lastReadAt`** — a per-participant timestamp, not a shared boolean on `Message` — because a Conversation may have more than two participants and a single flag cannot represent "read" correctly for all of them at once. A `Message` is considered read for a given participant when the message's `createdAt` is at or before that participant's `lastReadAt`; the future service layer owns updating `lastReadAt` and resolving timestamp/ordering edge cases. `lastReadAt` is read-state storage only — it never itself grants or implies authorization.
  - `Message` uses the same two-path author split (`authorStaffUserId`/`authorClientProfileId`), and this checkpoint adds one content-level database restriction beyond path exclusivity: a client-authored message can never have `visibility = INTERNAL_NOTE`.
  - `MessageAttachment` stores only the minimal metadata the backend-mediated storage boundary needs (`storageKey` unique, `fileName`, `mimeType`, `fileSizeBytes`) — never a public URL.
  - No Conversation status/lifecycle field, subject/title field, or `lastMessageAt` denormalization is added — none is defined anywhere in blueprint Section 10.
  - Conversation/message **authorization**, and the cross-table client-consistency invariants (`relatedBooking.clientId`/`relatedProposal.clientId` must equal `Conversation.clientId`; a `CLIENT` participant must belong to `Conversation.clientId`), are explicitly **not implemented** in this checkpoint. A future enforcement checkpoint must account for all of: Admin/Manager's full, unconditional visibility into every Conversation; a CLIENT actor's ownership of the Conversation's Client (via ClientProfile) together with explicit `ConversationParticipant` membership; a Travel Consultant's active Client/Booking assignment; and explicit `ConversationParticipant` membership for Finance/Visa Documentation actors, who have no assignment-based path onto a Conversation at all. Conversation authorization must never be described or implemented as "participant rows alone." Server-side exclusion of `INTERNAL_NOTE` messages from every client-facing query is likewise deferred to that same future checkpoint.
- **Rationale:** Directly follows Section 10.1's documented structure (thread/participants/messages/attachments, client-visible-vs-internal-note) and Section 10.2's closed category list, without inventing any undocumented field (status, title, `lastMessageAt`). The per-participant `lastReadAt` model was chosen over a shared Message-level boolean specifically because Section 10.1 describes more than two possible participants per thread (Travel Consultant, optional Finance, optional Visa Documentation, plus the Client), which a shared flag cannot represent correctly. The staff/client split-identity pattern on both `ConversationParticipant` and `Message` reuses this schema's established `StaffAssignment`/`ProposalAcceptance` precedent rather than inventing a new attribution shape.
- **Migration-history note:** This checkpoint's schema is split across two migrations rather than one, because of an implementation-session incident: `prisma migrate dev --create-only` was run a second time to confirm the first run's exit code, and Prisma's documented behavior of always applying any already-pending unapplied migration at the start of a `migrate dev` invocation (regardless of `--create-only` on that specific run) caused the first-generated migration — at that point containing only the auto-generated tables/enums/standard indexes/foreign keys, before any hand-written constraint had been added — to be applied to the local `heritage_v3_dev` database. Inspection confirmed: all four new tables were empty at the time (no data was ever at risk), no object outside the four new tables referenced them, and no pre-existing table's structure was altered. Rather than editing the already-applied migration file after the fact (which would desync it from the checksum Prisma already recorded against it in `_prisma_migrations`, and `prisma migrate resolve --rolled-back` is not a valid operation against a migration that completed successfully — it did not fail), the remediation was forward-only: migration `20260717010445_conversation_schema_foundation` (tables/enums/standard indexes/FKs) was left byte-for-byte unchanged; the second, previously-empty migration was renamed to `20260717010520_conversation_schema_constraints`, populated with every hand-written PostgreSQL CHECK constraint and partial unique index this checkpoint requires, and reviewed. Following that review, **both migrations were successfully applied to local `heritage_v3_dev` on July 17, 2026** via `prisma migrate dev` (the base migration was already applied from the incident above; only the constraints migration was newly applied in this step). `prisma migrate status` subsequently reported all 8 migrations applied and the schema up to date. A read-only PostgreSQL catalog check confirmed all four hand-written CHECK constraints (`conversation_related_record_exclusive`, `conversation_participant_identity_role_match`, `message_author_path_exclusive`, `message_client_author_not_internal_note`) are present and validated, and both partial unique indexes (`conversation_participant_active_staff_key`, `conversation_participant_active_client_profile_key`) are present, unique, and valid with the correct predicates. This application is confirmed for local `heritage_v3_dev` only — application to staging or production has not occurred as part of this checkpoint and must be verified independently before either environment is considered current.
- **Constraint:** No later checkpoint should combine these two migrations or edit either one's SQL after the fact. Conversation/message authorization, cross-client consistency checks, VisaCase as a third related-record type, email notification delivery (Section 10.3), and attachment malware scanning/signed-URL issuance (Section 12.3) all remain open for a future checkpoint, not resolved here. Conversation-creation authorization (who may open a Conversation, and whether a client may self-initiate one for particular categories) and the exact policy governing who may author a Message (CLIENT ownership plus active participation; explicit active participation for Finance/Visa Documentation; Travel Consultant assignment with the participant-row question still open; and whether Admin/Manager may post by role alone without participant membership) are both likewise left open — authorship foreign keys alone must never be treated as proof of authorization by any future implementation.
- **Effect:** Implements the Conversation Schema Foundation slice of the Phase 1 "Implement database schema and reviewed migrations from the approved Phase 0 entity plan" checklist item in `docs/HERITAGE_V3_TASK_BOARD.md`. Payment, Document, and VisaCase schema remain unimplemented, so that checklist item is not marked complete by this decision.

## D-017 — Visa Case Schema Foundation: MVP granularity, status list, and Stage A schema shape

- **Status:** Accepted
- **Date accepted:** July 17, 2026
- **Decision:** The Visa Case Schema Foundation checkpoint (blueprint Sections 4.5, 4.7, 5, 5.1, 5.2, 8, 13.8, 14.1, 14.8) is implemented in stages; this entry covers **Stage A (schema-and-decision-documentation only — `schema.prisma` and this decisions-log entry, with no migration created or applied)**. Approved:
  - **One VisaCase per Booking for the MVP.** A Booking may have zero or one VisaCase; a VisaCase belongs to exactly one Booking. Enforced by `VisaCase.bookingId String @unique` — a plain unique constraint, not a partial one, since this checkpoint has no historical/superseded VisaCase concept for a partial index to distinguish. Multiple historical or simultaneous VisaCases per Booking, and traveler-level VisaCase modeling (one case per traveler on a multi-traveler Booking), are both explicitly out of scope.
  - **The exact nine-value `VisaCaseStatus` enum:** `OPENED`, `REQUIREMENTS_PENDING`, `UNDER_REVIEW`, `ADDITIONAL_INFORMATION_REQUIRED`, `READY_FOR_SUBMISSION`, `SUBMITTED`, `APPROVED`, `REJECTED`, `WITHDRAWN`, with `APPROVED`, `REJECTED`, and `WITHDRAWN` as terminal. This is the one status enum in this schema whose values are set by explicit decision rather than adopted directly from blueprint text — blueprint Section 13.8 states "the detailed visa status list will be finalized alongside implementation planning" and Section 16.2 separately lists it as an open decision; this entry is that finalization. No transition matrix is adopted or implied by the enum's declaration order or by which values are marked terminal — transition enforcement (including enforcing terminality) is explicitly deferred to a later service/API checkpoint, mirroring how `BookingStatus`'s transition matrix was deferred to its own later, separate D-014 checkpoint.
  - **Direct `Client` and `Booking` relations on `VisaCase`**, mirroring this schema's established `Lead.clientId`/`Proposal.clientId`/`Booking.clientId`/`Conversation.clientId` convention, both `onDelete: Restrict`. `VisaCase.clientId` must always equal the Client reachable through `VisaCase.booking.clientId` — a cross-record rule Prisma cannot enforce, deferred to mandatory service-layer verification at write time, the same way `Booking.clientId` vs. its `ProposalVersion.proposal.clientId` is already deferred. No duplicated or derived-column schema logic was used to attempt to solve this.
  - **VisaCase as a StaffAssignment target at the schema level only.** `StaffAssignment.visaCaseId` (nullable) is added in Stage A; the existing three-target XOR CHECK constraint and the corresponding partial unique active-assignment index are **not yet altered in any database** — a later migration-generating stage must extend `staff_assignment_lead_xor_client_xor_booking` to a four-target `staff_assignment_lead_xor_client_xor_booking_xor_visa_case` (`CHECK (num_nonnulls("leadId", "clientId", "bookingId", "visaCaseId") = 1)`) and add `staff_assignment_active_visa_case_key` (`WHERE "endedAt" IS NULL AND "visaCaseId" IS NOT NULL`). `features/assignments`' `TargetKind` union, service, audit, and authorization code are untouched in Stage A and remain so until a separate, later assignment-enforcement checkpoint, mirroring D-015's precedent for Booking exactly.
  - **VisaCase as the third optional Conversation related-record target at the schema level only.** `Conversation.relatedVisaCaseId` (nullable) is added in Stage A; the existing two-column `conversation_related_record_exclusive` CHECK is **not yet altered in any database** — a later migration-generating stage must replace it with `CHECK (num_nonnulls("relatedBookingId", "relatedProposalId", "relatedVisaCaseId") <= 1)`.
  - **Every `VisaStatusHistory` row requires an attributable staff actor under D-017's MVP policy.** `changedByUserId` is required, not nullable, matching `BookingStatusHistory` rather than `LeadStatusHistory`. Blueprint Section 5.1 permits deliberate creation through an explicit staff or system action; D-017 deliberately narrows the current MVP schema to staff-attributed creation and status history. A future automated or actorless VisaCase transition would require a superseding decision and schema change.
  - **`VisaRequirement` and all Document entities (`Document`, `DocumentRequirement`, `DocumentReview`) are deferred**, not modeled even as a placeholder. `VisaRequirement`'s one-sentence blueprint description (Section 14.8: "defines what is required for a specific VisaCase (documents, forms, deadlines)") overlaps structurally with `DocumentRequirement` (Section 14.7: "defines which document categories are required for a given Booking or VisaCase"), and neither `Document` nor `DocumentRequirement` exists anywhere in this schema yet.
  - **Assignment-service wiring, VisaCase authorization, the status-transition matrix, API routes, admin dashboard and client portal UI, and notifications are all deferred** to later, separate checkpoints — none is implemented, implied, or assumed by Stage A's schema shape.
  - **No migration has been generated or applied during Stage A.** No `prisma migrate` command was run. `schema.prisma`'s new and changed models, fields, relations, and doc comments do not correspond to any database table, column, constraint, or index anywhere — local, staging, or production — until a later stage generates and a still-later stage applies the migration.
- **Rationale:** Blueprint Section 5.2's conceptual diagram presents VisaCase as a singular conditional relationship (`Booking --(conditional, only if required)--> Visa Case`) and Section 8 confirms a visa case is conditional and never automatic, but neither section independently defines complete cardinality — the blueprint does not itself state whether a Booking could ever have more than one VisaCase over time. D-017 is the explicit decision establishing zero or one VisaCase per Booking for the MVP, chosen because it avoids adding an unapproved Traveler entity or storing loosely modeled applicant identity data during the MVP. The plain-unique (not partial-unique) `bookingId` constraint reflects that this checkpoint has no "current vs. superseded" VisaCase concept to distinguish, unlike `ProposalVersion` or `StaffAssignment`. Deferring `VisaRequirement` and Document entities avoids prematurely designing overlapping structures before the document domain (`Document`/`DocumentRequirement`) is implemented, consistent with this schema's established caution about not modeling a shape that would likely need reworking (e.g. TourPackage deferred entirely). Staging the checkpoint (schema-and-decision-documentation-only Stage A, migration-generation Stage B, application in a still-later stage) is a direct, deliberate response to the D-016 migration-history incident: keeping schema editing, migration generation, and migration application as separate, individually-reviewable steps reduces the chance of a repeat, and Stage A explicitly documents that Stage B must invoke `prisma migrate dev --create-only` exactly once.
- **Constraint:** The four-target `StaffAssignment` XOR CHECK, its `visaCaseId` partial unique index, the three-target `Conversation` related-record CHECK, and the `visa_status_history_status_changed` CHECK are all specified here as requirements for the future migration-generating stage but must not be added to any migration file during Stage A. Who may create or change a VisaCase (beyond Visa Documentation Staff, blueprint Section 4.5), whether Admin/Manager's Section 4.2 "full visibility" extends to VisaCase edit capability, and how VisaCase-level and Booking-level `StaffAssignment` should interact are all left open, not resolved here.

## D-018 — Document Schema Foundation: single-entity versioning, derived status, and requirement/context boundaries

- **Status:** Accepted
- **Date accepted:** July 17, 2026
- **Decision:** The Document Schema Foundation checkpoint (blueprint Sections 4.2–4.6, 12.1–12.3, 13.1, 13.3, 13.4, 13.7, 14.7) is implemented in stages; this entry covers **Stage A (schema-and-decision-documentation only — `schema.prisma` and this decisions-log entry, with no migration created or applied)**. Approved:
  - **Single-entity versioning, no `DocumentVersion` model.** Each `Document` row represents one immutable uploaded file/version. A replacement creates a new `Document` row linked back to the original through `previousDocumentId`; the replaced row is retained, never deleted or mutated (blueprint Section 12.2: "a replaced document is retained, not deleted"). Unlike Proposal/ProposalVersion (blueprint Section 14.4, which explicitly names both), Section 14.7 names only `Document` itself with "version" as one of its own fields — no separate `DocumentVersion` entity is introduced.
  - **`Document.status` is not stored; no `DocumentStatus` enum exists.** Operational status is derived by the future service/repository layer in this exact priority order: (a) if another `Document` references the current row through `previousDocumentId` — equivalently, the current row's `replacementDocument` reverse relation is non-null — the current (older) row is SUPERSEDED/REPLACED, regardless of any `DocumentReview` it may also carry; (b) otherwise, if the current `Document` has no `DocumentReview` rows at all, it is PENDING_REVIEW; (c) otherwise, its status is the latest `DocumentReview.outcome`, with "latest" selected deterministically using `reviewedAt DESC, createdAt DESC, id DESC` — a service/repository ordering rule, not a new database constraint or index requirement. `DocumentReviewOutcome` (`APPROVED`, `REJECTED`, `REPLACEMENT_REQUESTED`) is the only closed enum this checkpoint adds, taken directly from blueprint Section 14.7's own closed three-value list.
  - **`documentRequirementId` is nullable.** Proactive or ad-hoc uploads are permitted; a document counts toward a formally requested requirement only when explicitly linked. Nothing in blueprint Section 12.1 mandates a requirement-first workflow.
  - **Context targeting.** `Document.clientId` is always required (direct FK, mirroring this schema's established convention). A `Document` may additionally target at most one of `bookingId`/`visaCaseId` (never both) — a client-only Document with both null is permitted. `DocumentRequirement` targets exactly one of `bookingId`/`visaCaseId` (never neither, never both) — read from blueprint Section 12.1's "linked to a DocumentRequirement that defines what is required for a given booking **or** visa case."
  - **Direct-context ownership invariants (cross-row, service-layer only — not expressible as a Prisma/PostgreSQL CHECK across related tables).** If `Document.bookingId` is non-null, the referenced `Booking.clientId` must equal the Document's own `clientId`; if `Document.visaCaseId` is non-null, the referenced `VisaCase.clientId` must equal the Document's own `clientId`. Both checks apply unconditionally — including when `documentRequirementId` is null — because a Document's context ownership must hold regardless of whether it happens to be requirement-linked. When `documentRequirementId` is set, the linked `DocumentRequirement`'s own target (`bookingId` or `visaCaseId`) must exactly match the Document's target of the same kind and resolve to the same Client as the Document's `clientId`; a requirement-linked Document must never be client-only (a non-null `documentRequirementId` requires exactly one of `bookingId`/`visaCaseId` also non-null). All of these are deferred to mandatory transactional service-layer verification at write time, the same way this schema already defers the analogous `Booking.clientId`/`VisaCase.clientId` cross-row checks elsewhere.
  - **Uploader-identity invariants (cross-row, service-layer only — no database role/status column or CHECK is added).** The `document_uploader_path_exclusive` CHECK proves only that exactly one of `uploadedByStaffUserId`/`uploadedByClientProfileId` is populated; it proves nothing about the referenced identity's role, account status, or ownership. When `uploadedByClientProfileId` is used, the referenced `ClientProfile.clientId` must equal the Document's own `clientId`. `uploadedByStaffUserId` may only ever represent an authenticated, active, operationally-authorized staff actor at write time — a CLIENT-role `User` must never be recorded via `uploadedByStaffUserId`. Exact per-role upload capability boundaries remain deferred to the future Document service/API checkpoint, matching this schema's existing deferral of analogous role-boundary enforcement elsewhere.
  - **Replacement integrity.** `previousDocumentId` is nullable and `@unique`, preventing two Documents from sharing one predecessor (a replacement-chain fork). Services must ensure a replacement retains the same client/context/requirement/category lineage as the row it replaces and increments `version` by exactly one. Long-cycle prevention (proving a replacement chain terminates) remains a service-layer invariant; the `@unique` constraint alone cannot prove it.
  - **Review reason.** A non-blank `reason` is required on `DocumentReview` when `outcome` is `REJECTED` or `REPLACEMENT_REQUESTED`, per `.claude/rules/admin-dashboard.md`'s explicit rule that rejecting a document requires a logged reason; `APPROVED` may carry an optional reason/note. The later migration must enforce this with `CHECK ("outcome" NOT IN ('REJECTED', 'REPLACEMENT_REQUESTED') OR COALESCE(length(btrim("reason")), 0) > 0)` — the `COALESCE` guard is required, not a plain `IS NOT NULL` check or a bare `length(btrim(reason)) > 0`, because PostgreSQL treats a CHECK expression that evaluates to `NULL` as satisfied, and a bare `length(btrim(NULL))` comparison would silently evaluate to `NULL` (and therefore pass) for a `REJECTED`/`REPLACEMENT_REQUESTED` row with no reason at all.
  - **Reviewer-identity invariants (cross-row, service-layer only — no new enum, role field, or database constraint is added).** `reviewedByUserId` being a required, non-nullable FK to `User` proves only that a `User` row is referenced, not that User's role or account status. It is a service-layer invariant, not a database constraint, that `reviewedByUserId` must resolve to an authenticated, active, operationally-authorized staff actor at write time; a CLIENT-role `User` must never create, or be recorded as, a `DocumentReview`. The exact capability boundary between Admin/Manager, Travel Consultant, and Visa Documentation Staff for which review outcomes each may record remains deferred to the future Document service/API checkpoint, consistent with this schema's existing deferral of analogous role-boundary enforcement elsewhere — that deferral concerns only which staff roles may review, not whether clients may; clients reviewing documents is out of scope under every reading of blueprint Section 4.
  - **VisaRequirement boundary.** `DocumentRequirement` owns uploadable document-category obligations for both Bookings and VisaCases. Future `VisaRequirement` work (still fully deferred) may model broader visa procedural requirements, forms, and deadlines, but must not duplicate `DocumentRequirement`'s uploadable-document responsibility — resolving the overlap D-017 itself already flagged between blueprint Sections 14.7 and 14.8.
  - **Access/download logging deferred.** `ActivityLog`-based access and download tracking (blueprint Section 12.3: "access and download audit logs for every document") is deferred to Phase 4 implementation and must exist before document access/download endpoints are considered complete. The existing `AuditLog` model remains scoped to sensitive/security-relevant staff actions and must not be repurposed as the routine download-event store.
  - **Storage metadata boundary.** Only the storage-metadata fields already established by `MessageAttachment` are used: `storageKey` (an internal private-storage key, never a permanent public URL), `fileName`, `mimeType`, `fileSizeBytes`. No storage-provider/bucket identifier, checksum, malware-scan-status, or document-content field is added in this checkpoint — none is blueprint-required, and ADR-001 places actual malware-scanning/storage-provider configuration in Phase 4, alongside the Documents feature.
  - **No migration has been generated or applied during Stage A.** No `prisma migrate` command was run. `schema.prisma`'s new and changed models, fields, relations, and doc comments do not correspond to any database table, column, constraint, or index anywhere — local, staging, or production — until a later stage generates and a still-later stage applies the migration.
- **Rationale:** Blueprint Section 14.7 names exactly three entities (`Document`, `DocumentRequirement`, `DocumentReview`) with no separate version or submission entity, and describes `Document` itself as carrying "category, version, and status" as its own fields — the single-entity-with-version reading follows that literal text rather than inventing a fourth entity blueprint doesn't name. Deriving status rather than storing it mirrors this schema's established aversion to redundant derived state (e.g. `ProposalVersion`'s accepted/locked state). The nullable `documentRequirementId` and permissive client-only-Document shape avoid over-constraining a workflow blueprint Section 4.6 describes clients as free to use ("Upload, view, and track their own documents") without a stated requirement-first precondition. Deferring `ActivityLog`, storage-provider/checksum fields, and `VisaRequirement` avoids modeling entities or columns this checkpoint has no blueprint-sourced shape for, consistent with this schema's established caution against premature, likely-to-be-reworked design (the same reasoning D-017 applied to `VisaRequirement`/Document entities before this checkpoint existed to resolve it).
- **Constraint:** The `document_requirement_target_exclusive`, `document_context_exclusive`, `document_uploader_path_exclusive`, `document_version_positive`, `document_previous_not_self`, and `document_review_reason_required` CHECK constraints are all specified here as requirements for the future migration-generating stage but must not be added to any migration file during Stage A. Whether Admin/Manager's Section 4.2 "full visibility" extends to document review/approval capability, and how Travel Consultant's "excluding visa-category documents" boundary (Section 4.3) is enforced against `Document.category` at the service layer, are both left open, not resolved here.
- **Effect:** Implements Stage A (schema-and-decision-documentation only) of the Document Schema Foundation slice of the Phase 1 "Implement database schema and reviewed migrations from the approved Phase 0 entity plan" checklist item in `docs/HERITAGE_V3_TASK_BOARD.md`. That checklist item remains unchecked: Payment schema remains unimplemented, and Document itself has no migration yet. `docs/HERITAGE_V3_TASK_BOARD.md` is not updated by this entry — its own update is a later step.

## D-019 — Payment Schema Foundation: currency-per-Booking, allocation model, refund correction, and Stage A schema shape

- **Status:** Accepted
- **Date accepted:** July 20, 2026
- **Decision:** The Payment Schema Foundation checkpoint (blueprint Sections 4.2-4.7, 5.1-5.2, 11.1-11.7, 13.4, 13.6, 14.5, 14.6) is implemented in stages; this entry covers **Stage A (schema-and-decision-documentation only — `schema.prisma` and this decisions-log entry, with no migration created or applied)**. Approved:
  - **Currency refinement** (supersedes D-002's PHP-only-MVP wording without deleting it — see D-002's own Refinement note above). Each Booking selects exactly one currency (`Booking.currencyCode`); PHP and USD are supported examples, not an exhaustive list; every financial amount within that Booking uses that Booking's selected currency; mixed-currency and exchange-rate handling within a single Booking are deferred.
  - **`Booking.totalAmount`/`currencyCode` are added, both nullable.** Neither field can be required from day one: `createBookingSchema` accepts only `proposalVersionId` today, and `ProposalVersion` carries no pricing content yet, so no source exists to populate either field at Booking-creation time; a `NOT NULL` column without a default would also fail to apply against any existing Booking row. Both fields must exist (be non-null) before a `PaymentPlan` may be created for that Booking, and neither may change once a `PaymentPlan` or `Payment` exists for it — both service-layer invariants, not database-enforced (no trigger mechanism is used anywhere in this schema).
  - **One `PaymentPlan` per `Booking` for the MVP** (`PaymentPlan.bookingId @unique`, a plain unique index, mirroring `VisaCase.bookingId`'s own precedent). `PaymentPlan` does not duplicate `totalAmount`, `currencyCode`, or a separate deposit-amount field.
  - **Deposit represented as `Installment.isDeposit Boolean`**, the smallest justified field for this checkpoint's evidence — not a new enum. A migration-only partial unique index enforces at most one deposit Installment per plan; the future service layer must additionally enforce that a deposit, when present, is `sequenceNumber = 1`. Whether any given plan requires a deposit at all follows that plan's own approved booking terms — blueprint Section 11.4 does not state every plan must include one, so this checkpoint does not assume universality.
  - **No stored Installment status and no waiver fields.** Installment payment state (Scheduled/Due/Overdue/Partially Paid/Paid) is fully derived from allocations, refunds, due date, and amount by the future service layer. No approved requirement in this repository supports installment waivers (blueprint Section 11.6 lists "Waived" only as one illustrative example within a still-unfinalized list), so no `waivedAt`/`waivedByStaffUserId`/`waivedReason` field is added.
  - **`Payment` targets `Booking` and `Client` directly, never `installmentId`.** Which Installment(s) a Payment covers is recorded through the new `PaymentAllocation` join model instead, supporting one Payment covering multiple Installments, one Installment receiving multiple Payments, and partial payments (blueprint Section 11.4) — a shape a single nullable `installmentId` column cannot express. `Payment` carries no inline confirm/reject/reverse/refund timestamp, actor, or reason field; every transition is recorded on the new append-only `PaymentStatusHistory` instead, mirroring `BookingStatusHistory`'s established convention, so `Payment.status` can never drift out of sync with a duplicated field set.
  - **`PaymentAllocation.amount` is always positive, never signed.** This model is append-only: a misallocation is corrected by writing a `PaymentAllocationReversal` (a complete, one-time reversal of exactly one allocation — `paymentAllocationId @unique`) and then creating new, separate positive `PaymentAllocation` rows, never by mutating or deleting the original. A `PaymentAllocation` with any existing `PaymentRefundAllocation` rows against it must not be reversed unless the service can prove the reversal preserves every refund-allocation invariant; default service policy is to reject that operation. A confirmed amount left unallocated to any Installment is unapplied Booking credit and is never automatically applied to a future Installment.
  - **`PaymentRefund` is a separate, append-only record** — a row exists only once money has actually been returned, so this checkpoint models no "pending refund" state. Multiple partial refunds against one Payment are supported. A Payment stays `CONFIRMED` while partially refunded and becomes `REFUNDED` only once cumulative refunds equal its full amount; a Payment with any refund must never transition to `REVERSED` (refunded and reversed are mutually exclusive); refund totals must never exceed the original Payment amount. `PaymentRefundAllocation` links a `PaymentRefund` to the specific `PaymentAllocation` row(s) it reduces (positive amount, `@@unique([paymentRefundId, paymentAllocationId])`), preserving exactly which Installment's balance reopens; any refunded amount not linked to an allocation is a refund from unapplied Booking credit.
  - **Corrected net-contribution formula, fixing an earlier draft's defect.** An earlier draft computed "gross confirmed payment total" using only `status = CONFIRMED` while separately subtracting all refunds regardless of status, so a fully refunded Payment (whose status becomes `REFUNDED`, no longer `CONFIRMED`) produced a *negative* net contribution instead of exactly zero. The corrected, approved formula is: `net contribution of Payment P = CASE WHEN P.status IN (CONFIRMED, REFUNDED) THEN P.amount - SUM(PaymentRefund.amount for P) ELSE 0 END`; `net confirmed amount paid = SUM(net contribution of every Payment under the Booking)`; `remaining Booking balance = max(Booking.totalAmount - net confirmed amount paid, 0)`; `overall Booking overpayment = max(net confirmed amount paid - Booking.totalAmount, 0)`; `net active allocation (Installment Y) = SUM(PaymentAllocation.amount WHERE installmentId = Y AND payment.status IN (CONFIRMED, REFUNDED) AND no PaymentAllocationReversal exists for that allocation) - SUM(PaymentRefundAllocation.amount for those allocations)`; `unapplied Booking credit = net confirmed amount paid - SUM(net active allocation across every Installment)`; `outstanding Installment amount = max(Installment.amount - net active allocation, 0)`; `next payment due = earliest dueDate among installments with outstanding amount > 0`. The service layer must guarantee unapplied Booking credit and every net active allocation can never become negative, by actively verifying it at write time. This formula also required a narrow clarification to `docs/HERITAGE_V3_PROJECT_BLUEPRINT.md`'s Section 11.1/11.2 (made alongside this entry) — the blueprint's "Refunded" status-effect row was worded at the whole-payment-status level, before partial refunds were an approved feature; the amendment clarifies that a partially refunded Payment stays `CONFIRMED` and reduces the balance only by its refunded portion.
  - **`PaymentStatus` is the exact seven-value closed list from blueprint Section 11.2's table** (`PENDING`, `CONFIRMED`, `REJECTED`, `CANCELLED`, `FAILED`, `REFUNDED`, `REVERSED`). No `VOIDED` or `PARTIALLY_REFUNDED` value is added.
  - **`PaymentStatusHistory`** mirrors `BookingStatusHistory` exactly (append-only, required actor, nullable `previousStatus` only for the initial row). Every real transition after the initial `PENDING` record requires a non-blank `reason` (standardized, service-generated reasons are acceptable) — stricter than `document_review_reason_required`'s outcome-conditional pattern. `idempotencyKey` is required specifically for transitions to `CONFIRMED`, `REVERSED`, or `REFUNDED`. `Payment.status`, this history row, and the required `AuditLog` entry must be written in one future transaction.
  - **Idempotency keys** are added to `PaymentAllocation`, `PaymentAllocationReversal`, `PaymentRefund`, and (conditionally) `PaymentStatusHistory` — each required and unique, since none of these writes has a natural uniqueness to detect a retry by (unlike `Booking.proposalVersionId`). The future service layer must check for an existing row by the caller-supplied key before inserting and return that result on a retry, exactly mirroring `bookings/service.ts`'s existing handling of a `bookingReference`/`proposalVersionId` unique-constraint race.
  - **`Receipt` is an immutable historical snapshot** — `amount` and `currencyCode` captured at issuance, no `updatedAt` field, one per Payment (`paymentId @unique`, already anticipated by `.claude/rules/database-security.md`'s "one confirmed Receipt per confirmed Payment" example), issued only for a validly confirmed Payment, and never deleted or mutated by a later reversal or refund. No receipt-number prefix format is enforced — only uniqueness.
  - **`Document.paymentId` (nullable) reuses the existing Document/DocumentReview machinery** for client-submitted payment-proof evidence, rather than a parallel review model. The existing `document_context_exclusive` CHECK is widened from two columns to three (`num_nonnulls("bookingId", "visaCaseId", "paymentId") <= 1`), following the exact drop-and-re-add pattern already used for the Visa Case Schema Foundation's widening. `DocumentReview`'s role-boundary doc comment is narrowly amended: Finance/Accounting may review a Document only when its `paymentId` is non-null — a structural check, not a `category` string match, since `Document.category` remains free-text with no closed list or CHECK constraint (blueprint Section 12.1); no `PAYMENT_PROOF` category constant or CHECK is invented. Approving/rejecting such a Document and the corresponding `Payment.status` transition must occur atomically in a future service layer.
  - **No `StaffAssignment` target for Payment or PaymentPlan.** Payment authorization derives entirely from the existing Booking-level assignment; no new target column is added.
  - **No migration has been generated or applied during Stage A.** No `prisma migrate` command was run. `schema.prisma`'s new and changed models, fields, relations, and doc comments do not correspond to any database table, column, constraint, or index anywhere — local, staging, or production — until a later stage generates and a still-later stage applies the migration.
- **Rationale:** The corrected net-contribution formula, one-PaymentPlan-per-Booking, positive-only append-only allocations with a dedicated reversal model, and a dedicated `PaymentStatusHistory` all follow this schema's established preference for append-only history and derived state over mutable or duplicated fields (`Document.status`, `ProposalVersion`'s accepted/locked state, `BookingStatusHistory`). Modeling `Payment` against `Booking` directly, with allocation as a separate join, follows blueprint Section 14.6's own "against an Installment or Booking" phrasing literally rather than forcing a single FK to carry two different meanings. Deferring `PaymentAdjustment`, the refund documentation type, and the post-approval Installment amendment workflow avoids guessing at a shape this repository has no approved requirement for yet, consistent with this schema's established caution — the same reasoning D-017 and D-018 each applied to entities/fields they had no blueprint-sourced shape for.
- **Constraint:** The `booking_total_amount_positive`, `booking_financials_pairing`, `booking_currency_code_format`, `payment_plan_approval_pairing`, `installment_amount_positive`, `installment_active_deposit_key` (partial unique index), `payment_amount_positive`, `payment_status_history_status_changed`, `payment_status_history_reason_required`, `payment_status_history_idempotency_key_required`, `payment_allocation_amount_positive`, `payment_allocation_reversal_reason_required`, `payment_refund_amount_positive`, `payment_refund_reason_required`, `payment_refund_allocation_amount_positive`, `receipt_amount_positive`, `receipt_currency_code_format`, and the widened `document_context_exclusive` constraints are all specified here as requirements for the future migration-generating stage but must not be added to any migration file during Stage A. Whether `Installment` corrections after `PaymentPlan` approval require their own append-only pattern, and the exact `PaymentAdjustment` shape, are both left open, not resolved here.
- **Deferred:** `PaymentAdjustment` is not modeled until its exact balance effect is approved. The refund documentation type (a refund reference, credit note, or equivalent client-facing document, blueprint Section 11.5/16.2) remains open — `PaymentRefund` is a structured internal financial record only, not automatically that document. A post-approval Installment amendment/correction workflow is left open. Payment-gateway/processor fields, mixed-currency/exchange-rate handling within one Booking, an installment-status enum, and automatic credit-to-installment allocation are all explicitly excluded from this checkpoint.

## D-020 — Notification Schema Foundation: minimal in-app alert shape and Stage A schema

- **Status:** Accepted
- **Date accepted:** July 21, 2026
- **Decision:** The Notification Schema Foundation checkpoint (blueprint Section 14.9) is implemented in stages; this entry covers **Stage A (schema-and-decision-documentation only — schema.prisma and this decisions-log entry, with no migration created or applied)**. Approved:
  - **Notification is implemented as a minimal Phase 1 schema foundation now, rather than explicitly deferred to Phase 5.** Blueprint Section 15.3 lists Notifications as included in MVP, and D-019's own implementation-status update identified Notification as the sole remaining blueprint Section 14 entity with neither an implementation nor a documented deferral — this entry closes that specific gap.
  - **Each Notification belongs to exactly one required recipient `User`** (`Notification.recipientUserId`), never a split staff/client identity path. Blueprint Section 14.9 itself names a single "User (staff or client)" target; unlike `Message`/`ConversationParticipant`, whose staff/client identity split exists to record differing authorship semantics, a notification recipient requires no such split — every activated client account is already a `User` row (`ClientProfile.userId`).
  - **The recipient relation uses `onDelete: Restrict`**, matching this schema's established convention for a row that documents something about a User (`AuditLog.actorId`, `BookingStatusHistory.changedByUserId`, `PaymentStatusHistory.changedByUserId`) rather than the `onDelete: Cascade` convention reserved for pure account extensions (`Session`, `Account`, `StaffProfile`). This preserves a Notification if its recipient User is later deactivated — consistent with User accounts being deactivated, never deleted, under this model.
  - **`eventKey` is a free-form, stable string**, not a closed enum, because no authoritative source in this repository defines a complete notification-type list — unlike `VisaCaseStatus`, where D-017 resolved an explicitly blueprint-flagged open decision (blueprint Section 13.8/16.2), nothing flags Notification's event types as needing closure. No Notification enum of any kind is introduced by this checkpoint. Any illustrative event-key examples recorded in `schema.prisma`'s doc comments (e.g. `"payment.confirmed"`, `"document.rejected"`) are non-exhaustive and not reserved by this decision — the future notification-producing service defines the real set.
  - **Durable display content is `title` and `message`**, the minimum payload an in-app alert needs to render itself, both required (non-nullable) strings.
  - **An optional `actionPath` is an internal relative application path**, never a permanent public URL or an arbitrary external URL, mirroring `MessageAttachment.storageKey`'s established never-a-public-URL convention.
  - **No generic `resourceType`/`resourceId` pair and no JSON `metadata` field are added.** Unlike `AuditLog.entityType`/`entityId` (accepted there for forensic record-keeping, not a live client-facing dereference target), a polymorphic reference pair or open JSON field on a user-facing Notification would both lose referential integrity and risk becoming a place sensitive payment, document, visa, or conversation content gets copied in.
  - **Read state is `readAt DateTime?`**, not a mutable boolean or a separate read-history model, mirroring `ConversationParticipant.lastReadAt`'s established pattern. Notification has exactly one recipient (unlike Conversation's many-participants problem that required `lastReadAt` on its own join model), so a single nullable column on the Notification row itself is sufficient.
  - **Lifecycle fields are `createdAt` and `readAt` only** — no `updatedAt`, `expiresAt`, or `archivedAt`. No `updatedAt` is added because the one meaningful mutation this row can receive under this foundation — being marked read — already has its own dedicated, more precise timestamp (`readAt`); a generic `updatedAt` would duplicate rather than add information. No `expiresAt`/`archivedAt` is added because no retention or expiry policy is approved anywhere in this repository yet (D-003/D-004 remain Open).
  - **No deduplication/idempotency field is added in Stage A.** Unlike the Payment-domain idempotency keys (D-019), added because specific financially-sensitive writes had no natural uniqueness to retry against, no Notification-producing service, event-production rule, or background job exists yet to design a real retry/duplicate shape against — a dedup field now would be guessing at an undesigned need. This may be added additively once Phase 5's actual event-production and retry design is known.
  - **Notification represents the in-app alert only.** Email delivery (blueprint Section 10.3; ADR-001's email-notification boundary) remains a separate, later concern — no email provider, channel, sent timestamp, delivery-status, or delivery-attempt field is added. The portal remains the system of record; email is an outbound side effect, not modeled by this table.
  - **Indexes are `@@index([recipientUserId, createdAt])`** (a recipient's inbox ordered by creation time) **and `@@index([recipientUserId, readAt, createdAt])`** (filtering a recipient's unread notifications together with creation-time ordering).
  - **No hand-written PostgreSQL CHECK constraint or partial index is specified for this minimal shape.** Unlike every earlier schema-foundation checkpoint in this file (D-016 through D-019), each of which required at least one hand-written constraint because of nullable-FK exclusivity or a conditional-string requirement, this checkpoint's shape has neither — this is the first schema-foundation checkpoint requiring no migration hand-augmentation.
  - **Future service-layer invariants** — none enforced by this schema, all left to the future notification-producing/consuming service: non-blank `eventKey`/`title`/`message`; that `actionPath`, when present, is a genuine internal relative path; data minimization (title/message must never contain sensitive payment, document, visa, or private conversation content, nor any credential, token, or secret); recipient-scoped authorization on every read; and which platform event maps to which recipient(s).
  - **No migration has been generated or applied during Stage A.** No `prisma migrate` command was run. `schema.prisma`'s new `Notification` model and `User.notificationsReceived` relation do not correspond to any database table, column, constraint, or index anywhere — local, staging, or production — until a later stage generates and a still-later stage applies the migration.
- **Rationale:** Blueprint Section 14.9 gives Notification only a one-sentence description with no field list, type list, or delivery model — every field beyond the single required recipient relation is therefore a design inference, not a blueprint-stated requirement, and this entry records each inference's justification explicitly rather than presenting it as settled fact (mirroring D-017's and D-018's own discipline for VisaCase and Document, each of which had similarly thin blueprint text). The single required-`User`-recipient shape, `Restrict`-on-delete, free-form `eventKey`, and nullable-timestamp read state each directly reuse an already-established pattern elsewhere in this schema (`ClientProfile.userId`, `AuditLog`/`BookingStatusHistory`/`PaymentStatusHistory`'s actor-relation convention, `Document.category`'s free-text precedent, and `ConversationParticipant.lastReadAt`, respectively) rather than inventing a new one, consistent with this schema's established caution against premature, likely-to-be-reworked design (the same reasoning D-017 applied to VisaRequirement and D-019 applied to PaymentAdjustment). Omitting `resourceType`/`resourceId`, JSON `metadata`, deduplication, and every email-delivery field follows the same discipline in the opposite direction: each is a plausible future need with no current approved shape to build against, so none is guessed at now.
- **Constraint:** No hand-written PostgreSQL CHECK constraint or partial unique index is required by this checkpoint's minimal shape — a departure from D-016/D-017/D-018/D-019, each of which specified at least one for a future migration-generating stage. Should a future stage introduce any conditional or cross-column rule (e.g., a dedup key with conditional uniqueness), that constraint must be decided and documented in its own later entry, not silently added to a migration. Nothing in this entry authorizes generating or applying a migration; that remains a separate, later, explicitly authorized stage.
- **Deferred:** Notification repositories and services; event-production rules (which platform events produce a notification, and for which recipients); whether creation happens synchronously in the same transaction as its triggering write or via a background job; retry and deduplication behavior; API routes; admin dashboard and client portal notification UI; recipient-scoped authorization enforcement on every fetch; list and mark-read behavior; email delivery and delivery-attempt tracking; background workers; notification preferences and opt-out rules; expiry, archival, deletion, and retention rules; and tests and seed data. All remain future implementation work, most falling under Phase 5 ("notifications," docs/HERITAGE_V3_TASK_BOARD.md).
- **Effect:** Implements Stage A (schema-source and decision documentation only) of the Notification Schema Foundation slice of the Phase 1 "Implement database schema and reviewed migrations from the approved Phase 0 entity plan" checklist item in `docs/HERITAGE_V3_TASK_BOARD.md`. That checklist item remains unchecked during Stage A: no reviewed Notification migration has been generated or applied to any environment. After a later reviewed migration is successfully generated, hand-reviewed, and applied to local `heritage_v3_dev` (and verified, mirroring D-017/D-018/D-019's own Stage B/C verification pattern), Notification will resolve the final unresolved entity-plan blocker D-019's implementation-status update identified — but that verification has not occurred as part of this entry. `docs/HERITAGE_V3_TASK_BOARD.md` is not updated by this entry; its update belongs to its own later, separately authorized stage, exactly mirroring D-017/D-018/D-019's own discipline. ## D-022 — Lead Management Core authorization, lifecycle, duplicate detection, and API contract

- **Status:** Accepted
- **Date accepted:** July 23, 2026
- **Decision:** The Lead Management Core checkpoint (blueprint Sections 4, 5, 6, 13.2, 14.2; `docs/HERITAGE_V3_TASK_BOARD.md` Phase 2; D-009; D-014; D-021) is approved as follows. This entry is self-contained — it is the authoritative contract for implementation, not a pointer to a separate report.

  **1. Implementation boundary.** This checkpoint authorizes: manual staff Lead creation; paginated Lead listing; single-Lead retrieval; ordinary-field editing; lifecycle-transition enforcement; append-only `LeadStatusHistory`; duplicate detection against both Lead and Client using normalized email/phone; inquiry-source tracking; `AuditLog` coverage for every sensitive Lead mutation; assignment-based authorization; and automated unit, route, and real-PostgreSQL integration coverage. It explicitly defers: a Lead admin UI; public inquiry endpoints; CAPTCHA/Turnstile and public-endpoint rate limiting; Lead-to-Client conversion implementation; Client management; Proposal/ROS; Booking UI; notifications; and any infrastructure/deployment change. **The existing schema fully supports this checkpoint** (`Lead`, `LeadStatus`, `LeadStatusHistory`, `Client`'s normalized contact fields, `StaffAssignment`'s `leadId` target, and `AuditLog` are all already migrated, per migration `20260714024613_lead_client_assignment_foundation`) — **no schema change or migration is authorized or required by this decision.**

  **2. Role and assignment contract.**
  - `ADMIN_MANAGER`: may create, list (all Leads), retrieve, edit, and transition any Lead. An Admin-created Lead is **not** automatically assigned — the existing `/api/leads/[id]/assignment` endpoint remains the sole mechanism for assigning or reassigning it, unchanged by this decision.
  - `TRAVEL_CONSULTANT`: may manually create a Lead. **A TC-created Lead is atomically self-assigned to the creating TC in the same creation transaction** — that single transaction writes the `Lead` row, the initial `NEW` `LeadStatusHistory` row, a `StaffAssignment` row (`assignedStaffId` = `assignedByUserId` = the creating TC), a `LEAD_CREATED` audit entry, and a `LEAD_ASSIGNED` audit entry, all atomically. A TRAVEL_CONSULTANT may list, retrieve, edit, and transition only Leads they hold an active assignment for (reusing `features/assignments/authorization.ts`'s existing `canAccessLead` unchanged, per the Task Board's own "wire canAccessLead ... into the new Lead ... resource routes" item). A TRAVEL_CONSULTANT may **not** self-assign to an arbitrary *existing* Lead — self-assignment is authorized only as an atomic side effect of that TC's own creation of a *new* Lead. The existing `ADMIN_MANAGER`-only `/api/leads/[id]/assignment` endpoint is unchanged and remains the only way to assign/reassign any other Lead.
  - `SYSTEM_ADMINISTRATOR`, `FINANCE_ACCOUNTING`, `VISA_DOCUMENTATION`, `CLIENT`: no Lead create/list/retrieve/edit/status-change permission — `SYSTEM_ADMINISTRATOR` per blueprint Section 4.1's explicit boundary against automatic operational-client-data access, the others for lack of any blueprint basis, `CLIENT` per Section 4.6.
  - This resolves D-009(d)'s previously open Travel Consultant self-assignment question **only** for the specific case of a Travel Consultant manually creating a brand-new Lead. It does not authorize a Travel Consultant to self-assign to any pre-existing Lead, and it does not modify the existing Admin/Manager-only assignment endpoint or its authorization.

  **3. Field and validation contract.** Manual creation accepts: `fullName` (required, trimmed, 1–200 characters); `source` (required, trimmed, 1–200 characters, free text — no enum); `email` (optional, trimmed, max 320 characters); `phone` (optional, trimmed, max 50 characters); `notes` (optional, trimmed, max 2,000 characters). At least one of `email`/`phone` is required. A blank optional value normalizes to `null`, never an empty string. Initial `status` is always `NEW` and can never be supplied by the caller. Ordinary fields (`fullName`, `email`, `phone`, `source`, `notes`) remain editable at every status except `CONVERTED_TO_CLIENT`, which locks ordinary-field editing entirely. Editing `email` or `phone` always reruns duplicate detection.

  **4. Contact normalization contract.**
  - **Email:** trim the complete value; lowercase the complete value; store the result as `normalizedEmail`, kept separate from the submitted/display `email` value.
  - **Phone:** `phone` stores the trimmed submitted value unchanged (display form). `normalizedPhone` is derived by: (a) stripping every non-digit character from the submitted value; (b) if the result starts with a leading international `00` prefix, removing it; (c) if what remains already starts with `63`, preserving it as-is (already international PH format); (d) else, if what remains is 10 or 11 digits and starts with `0` (Philippine domestic format), replacing the leading `0` with `63`; (e) else, if what remains is 10 digits and starts with `9` (Philippine mobile without a leading 0), prepending `63`; (f) otherwise — the conservative fallback — using the digits-only remainder unchanged, inventing no country code for a pattern that matches none of the above. Exhaustive normalization tests are required, including that `"0917 123 4567"`, `"+63 917 123 4567"`, `"0063 917 123 4567"`, and `"9171234567"` all normalize to the identical `"639171234567"`.

  **5. Duplicate-detection contract.** Both `normalizedEmail` and `normalizedPhone` are compared against both `Lead` and `Client`, system-wide — never scoped to the caller's own assignments, since Section 6.2's "never lost" guarantee requires catching a match regardless of who (if anyone) is assigned to the existing record. Matches are only ever surfaced for staff review — this checkpoint never auto-merges, auto-rejects, auto-converts, or auto-changes status as a result of a match. The current Lead is excluded from its own edit-time duplicate check. Results are deduplicated by underlying record id: a record matching on both email and phone appears exactly once, with both channels listed. The matched record's `email`, `phone`, `notes`, and assignment data are never returned. Visibility is further shaped by the caller's own authorization: `ADMIN_MANAGER` receives full match metadata (record type, id, full name, Lead status where applicable, and matched channels) for every match; a `TRAVEL_CONSULTANT` receives that same metadata only for a matched Lead/Client they are independently authorized to access (via `canAccessLead`/`canAccessClient`) — for a match outside that TC's authorization, the response includes only a generic `restrictedMatchDetected: true` indicator, never the inaccessible record's id, name, status, type, match count, or assignment. Duplicate checking must never become a cross-assignment PII or record-existence oracle for a Travel Consultant.

  **6. Status transition contract.** A same-status request is `IDEMPOTENT_NO_OP`: it returns success, writes no `LeadStatusHistory` row, writes no audit entry, and this check runs *before* `expectedStatus` conflict handling — matching existing Booking behavior (D-014). Allowed monotonic forward transitions: `NEW`→`UNDER_REVIEW`, `NEW`→`CONTACTED`, `NEW`→`CONSULTATION_SCHEDULED`, `NEW`→`QUALIFIED`, `UNDER_REVIEW`→`CONTACTED`, `UNDER_REVIEW`→`CONSULTATION_SCHEDULED`, `UNDER_REVIEW`→`QUALIFIED`, `CONTACTED`→`CONSULTATION_SCHEDULED`, `CONTACTED`→`QUALIFIED`, `CONSULTATION_SCHEDULED`→`QUALIFIED` — every active-pipeline status may advance to any later active-pipeline status, not only the adjacent next one, reflecting that staff may legitimately skip intermediate stages within one real interaction. Every active-pipeline status (`NEW`, `UNDER_REVIEW`, `CONTACTED`, `CONSULTATION_SCHEDULED`, `QUALIFIED`) may also transition to `NOT_PROCEEDING`, `DUPLICATE`, `SPAM`, or `ARCHIVED`. Additional classification-to-archive transitions: `NOT_PROCEEDING`→`ARCHIVED`, `DUPLICATE`→`ARCHIVED`, `SPAM`→`ARCHIVED`. Corrective/reopening transitions, each requiring a mandatory reason: `NOT_PROCEEDING`→`UNDER_REVIEW`, `DUPLICATE`→`UNDER_REVIEW`, `SPAM`→`UNDER_REVIEW`, `ARCHIVED`→`UNDER_REVIEW`. A reason is also mandatory for every transition *into* `DUPLICATE` or `SPAM` (i.e., every active-pipeline-status→`DUPLICATE`/`SPAM` edge), not only the reopening edges. Every required `reason` must be trimmed, non-blank, and at most 500 characters. `QUALIFIED`→`CONVERTED_TO_CLIENT` is `DEFERRED_TO_CONVERSION_ENDPOINT`: the generic status endpoint returns a controlled `CONVERSION_ENDPOINT_REQUIRED` error rather than performing the transition, since Lead-to-Client conversion remains a future, explicit, separate checkpoint (Section 6.7). Every other source→`CONVERTED_TO_CLIENT` transition is rejected outright (not deferred — `QUALIFIED` is the only textually legitimate pre-conversion source, Section 6.7's "normally performed once a lead is Qualified"). `CONVERTED_TO_CLIENT` is terminal: its own same-status request remains an idempotent no-op, every outgoing transition is rejected, and ordinary-field editing is locked (Section 3 above). Every matrix cell not explicitly named above is rejected, including every backward move within the active pipeline (e.g. `QUALIFIED`→`UNDER_REVIEW` directly, without first passing through a closing/reopening status, is not permitted). Transition authorization is uniform: `ADMIN_MANAGER` may perform any transition on any Lead; `TRAVEL_CONSULTANT` may perform any transition only on an actively assigned Lead; there is no additional Admin-only carve-out for classification (`DUPLICATE`/`SPAM`) or restoration (`ARCHIVED`→`UNDER_REVIEW`) transitions specifically — audit logging and the mandatory-reason requirement on those edges are the accountability mechanism instead of a narrower role gate.

  **7. Concurrency, history, and audit contract.** Every status-change request supplies `expectedStatus`; a stale `expectedStatus` (current status no longer matches, and the request is not the same-status no-op case above) returns `LEAD_CONFLICT`. Actual status changes execute inside the existing `runSerializableWithRetry` mechanism (`@/lib/serializable-transaction`), exactly as `updateBookingStatus` does. Within that transaction, the `Lead` row update, the new `LeadStatusHistory` row, and the `LEAD_STATUS_CHANGED` `AuditLog` entry are written atomically. Manual creation writes an initial `LeadStatusHistory` row with `previousStatus: null`, `newStatus: NEW`, `changedByUserId`: the creating staff user's id. Audit actions introduced by this checkpoint: `LEAD_CREATED`, `LEAD_ASSIGNED` (written only for the TC self-assignment-at-creation case in Section 2), `LEAD_UPDATED`, `LEAD_STATUS_CHANGED`. Every audit snapshot is allow-listed and must never duplicate `fullName`, `email`, `phone`, `notes`, or an arbitrary request body into `AuditLog.beforeState`/`afterState`. Safe audit metadata is limited to: Lead `status`, `source`, `hasEmail`/`hasPhone` boolean flags, the list of `changedFields` (field names only, for `LEAD_UPDATED`), the assigned staff id (for `LEAD_ASSIGNED`), and the mandatory transition `reason` where applicable. `LEAD_UPDATED` specifically records which field names changed and the resulting contact-presence flags, never the previous or new PII values themselves — consistent with `.claude/rules/database-security.md`'s data-minimization principle and this schema's own established sanitize-snapshot convention (`sanitizeBookingSnapshot`, `sanitizeAssignmentSnapshot`).

  **8. API contract.** `POST /api/leads` (create), `GET /api/leads` (paginated list), `GET /api/leads/[id]` (retrieve), `PATCH /api/leads/[id]` (edit ordinary fields — mirrors the existing `PATCH /api/staff/[id]` convention), `PUT /api/leads/[id]/status` (transition status — mirrors the existing `PUT /api/bookings/[id]/status` convention). Pagination: `page` (default 1, minimum 1), `pageSize` (default 20, minimum 1, maximum 100), deterministic ordering by `createdAt` descending then `id` descending (matching `listBookingsForActor`). List filters: exact `status`, exact `source`, and a case-insensitive `search` across `fullName`, `email`, and `phone`. All routes use the existing `parseJsonBody`/`parseQuery`/`validationErrorResponse` conventions and the standard `{ error: { code, message } }` envelope. The existing anti-enumeration behavior for a Travel Consultant is preserved exactly: an inaccessible Lead and a nonexistent Lead id must produce the identical response (`LEAD_FORBIDDEN`, 403), never distinguishable, matching `BookingError`'s and `canAccessLead`'s already-documented convention. Controlled error codes cover at minimum: `ROLE_NOT_PERMITTED`, `LEAD_NOT_FOUND`, `LEAD_FORBIDDEN`, `LEAD_LOCKED`, `REASON_REQUIRED`, `INVALID_STATUS_TRANSITION`, `CONVERSION_ENDPOINT_REQUIRED`, `LEAD_CONFLICT`, `VALIDATION_ERROR`.
- **Rationale:** Truthful monotonic progression (Section 6) reflects that a single staff interaction can legitimately qualify a lead across several conceptual stages at once, rather than forcing an artificial, un-lived intermediate history the blueprint's Section 6.1 table never actually mandates as sequential gatekeeping. Atomic creation-time self-assignment for a Travel-Consultant-created Lead (Section 2) prevents the orphan-record outcome an unassigned-on-creation policy would otherwise produce — a TC who manually records a phone/walk-in/referral lead (Section 6.8) must retain working access to the record they just created, consistent with Section 6.4's assignment model, without requiring a separate, immediate Admin/Manager action just to make a newly created record visible again to its own creator. Reusing `canAccessLead` unchanged, and leaving the existing `/api/leads/[id]/assignment` endpoint untouched, preserves assignment-based least privilege (blueprint Section 4, D-009) exactly as already implemented, rather than introducing a second, parallel authorization path. Shaping duplicate-match visibility around the caller's own authorization (Section 5) closes an information-disclosure gap a flat, unscoped match response would otherwise open: duplicate detection must remain "never lost" system-wide (Section 6.2) without becoming a way for a Travel Consultant to learn the existence, name, or status of a Lead or Client they are not assigned to. Keeping `CONVERTED_TO_CLIENT` reachable only via a future, explicit conversion checkpoint (Section 6) preserves Section 6.7's "explicit staff action" requirement and Section 5.1's non-automatic-creation rule, and avoids this checkpoint silently building half of a conversion feature that Client management (still unimplemented) cannot yet support. Every mechanism reused here — `runSerializableWithRetry`, the `{error:{code,message}}` envelope, allow-listed audit snapshots, `parseJsonBody`/`parseQuery`, and the `PATCH`-for-fields/`PUT`-for-status route convention — is copied from already-reviewed, already-tested Booking, Assignment, and Staff-management code, not reinvented.
- **Constraint:** No `schema.prisma` change and no migration are authorized or required by this decision — `Lead`, `LeadStatus`, `LeadStatusHistory`, `Client`'s normalized contact fields, `StaffAssignment`'s `leadId` target and its existing XOR CHECK/partial-unique-index, and `AuditLog` already fully support every mechanism described above, per migration `20260714024613_lead_client_assignment_foundation`. This decision resolves D-009(d)'s Travel Consultant self-assignment question only for the specific creation-time case in Section 2 above — it does not authorize self-assignment to a pre-existing Lead by any role, and it does not modify `features/assignments/*` or the existing `/api/leads/[id]/assignment` endpoint in any way. This decision does not implement Lead-to-Client conversion, Client management, Proposal/ROS, or any admin-dashboard UI, and does not itself write any application code, schema, or migration.
- **Effect:** Authorizes implementation of the Phase 2 "Lead Management Core backend," "Lead lifecycle transition enforcement and LeadStatusHistory," "Duplicate detection using normalized contact fields," and "Inquiry-source tracking" checklist items in `docs/HERITAGE_V3_TASK_BOARD.md`. Does not itself mark any Task Board checklist item complete — that update is a later, separate step once the implementation and its automated/integration coverage actually exist and pass.

## D-023 — Lead Management Admin UI route, authorization, read-model, and testing contract

- **Status:** Accepted
- **Date accepted:** July 24, 2026
- **Decision:** The Lead Management Admin UI checkpoint (`docs/HERITAGE_V3_TASK_BOARD.md` Phase 2's "Lead management admin UI" item; ADR-001; D-021; D-022) is approved as follows. This entry is self-contained and is the authoritative implementation contract for this checkpoint.

  Lead-to-Client conversion remains excluded. `QUALIFIED` to `CONVERTED_TO_CLIENT` continues to surface `CONVERSION_ENDPOINT_REQUIRED`; the UI does not imitate or partially implement conversion.

  No existing field is removed or renamed; no existing request, role, assignment, error, or anti-enumeration contract changes. The repository reads the active `StaffAssignment` and assigned `User.name` through an explicit nested relation selection and maps the result to the approved DTO. Eligible Travel Consultant read.** Add `GET /api/assignments/travel-consultants`, authorized only for `ADMIN_MANAGER`. `SYSTEM_ADMINISTRATOR` remains excluded from this operational read, preserving the platform-security versus operational-management boundary. Query parameters follow existing conventions: optional trimmed `search` (maximum 200 characters), `page` defaulting to 1, and `pageSize` defaulting to 20 with a maximum of 100. The response is:

## D-024 — Lead-to-Client Conversion authorization, linking, assignment, concurrency, audit, API, and UI contract

- **Status:** Accepted
- **Date accepted:** July 28, 2026
- **Decision:** The Lead-to-Client Conversion checkpoint (blueprint Sections 5, 5.1, 5.2, 6.7, 13.3; D-006; D-009; D-021; D-022; D-023; `docs/HERITAGE_V3_TASK_BOARD.md` Phase 2's "Explicit Lead-to-Client conversion" item) is approved as follows. This entry is self-contained — it is the authoritative contract for implementation, not a pointer to a separate report.

  **1. Implementation boundary.** This checkpoint authorizes: the explicit Lead-to-Client conversion backend (blueprint Section 6.7) and the minimal Lead-detail conversion UI on `/admin/leads/[id]`. It explicitly does not authorize a Client CRUD/management backend or UI (a separate, later Phase 2 checklist item), portal invitation issuance, User account creation, Proposal/ROS creation, Booking creation, Payment Plan creation, Visa Case creation, or any notification — per blueprint Section 5.1's non-automatic-creation rule, conversion creates or links only a Client record and nothing else. No `schema.prisma` change and no migration are authorized or required by this decision (Section 12). No new runtime dependency is introduced; this checkpoint uses only already-installed packages and already-established internal conventions. `Client.status` (blueprint Section 13.3; D-021's open item (b)) remains unresolved and is not introduced by this decision — the `Client` model already omits it entirely, and nothing in this checkpoint depends on it.

  **2. Eligibility and authorization.** Conversion is available only for a Lead whose current status is `QUALIFIED` (blueprint Section 6.7; D-022 §6's existing `QUALIFIED → CONVERTED_TO_CLIENT` `DEFERRED_TO_CONVERSION_ENDPOINT` cell in `features/leads/transitions.ts`). `ADMIN_MANAGER` may convert any Lead in `QUALIFIED` status. `TRAVEL_CONSULTANT` may convert a `QUALIFIED` Lead only when they hold that Lead's current active assignment. Every other role (`SYSTEM_ADMINISTRATOR`, `FINANCE_ACCOUNTING`, `VISA_DOCUMENTATION`, `CLIENT`) remains prohibited from converting a Lead, consistent with D-022 §2's role boundary. Before the transaction (Section 6) opens, the route/service performs the same initial, role-aware, anti-enumerating check every other Lead mutation already performs, using the existing, unchanged `canAccessLead` (`features/assignments/authorization.ts`) — and, when the request additionally supplies `clientId` to link to an existing Client, the existing, unchanged `canAccessClient` (`features/assignments/authorization.ts`) for that specific Client id. Both functions run against the global Prisma client (`@/lib/db`'s `prisma` singleton) and cannot themselves execute inside `runSerializableWithRetry`'s transaction client; Section 6 specifies the transaction-local recheck of this identical policy that keeps authorization race-safe for the duration of the actual write. The existing role-aware anti-enumeration behavior is preserved exactly at this initial check: for `ADMIN_MANAGER` a missing Lead is `LEAD_NOT_FOUND` (404); for `TRAVEL_CONSULTANT`, an inaccessible or nonexistent Lead is indistinguishably `LEAD_FORBIDDEN` (403), matching D-022 §8 and `LeadError`'s existing documented convention.

  **3. Create-new versus link-existing behavior.** The conversion action is `POST /api/leads/[id]/conversion`. Its request body is strict: `{ expectedStatus: "QUALIFIED", clientId?: string }` — no other property is accepted. An omitted `clientId` requests creation of a new Client from the Lead's own data. A supplied `clientId` requests linking to that existing Client. A link candidate is valid only when it matches the Lead on at least one of the Lead's current normalized contact channels — normalized email or normalized phone (the same `normalizedEmail`/`normalizedPhone` comparison D-022 §5 already establishes for duplicate detection); linking to an unrelated Client sharing no matching channel is prohibited. Before creating or linking, conversion always re-runs Client duplicate detection using the Lead's current normalized email/phone, reusing the existing `features/leads/repository.ts`'s `findDuplicateClientMatches` unchanged. Creating a new Client is permitted only when this re-run detection finds no matching Client system-wide; if any Client matches, the request must instead supply one of the matching `clientId` values (`CLIENT_MATCH_REQUIRES_LINK`, Section 9) — conversion never auto-links or auto-selects among multiple matching Clients on the caller's behalf; staff must explicitly choose one authorized candidate. Match visibility mirrors D-022 §5's existing duplicate-visibility shaping exactly: a `TRAVEL_CONSULTANT` never receives the id, name, count, or any other metadata of a matching Client they cannot access via `canAccessClient` — only a `restrictedMatchDetected: true` indicator, with no further detail. An accessible candidate exposes only `id`, `fullName`, and the matched channel(s) (`EMAIL`/`PHONE`) — never `email`, `phone`, `notes`, any other profile field, or assignment data, matching D-022 §5's field-level restriction on duplicate-match responses. When every matching Client available to a `TRAVEL_CONSULTANT` is restricted (none independently accessible), creation of a new Client is blocked outright — the TC cannot bypass an inaccessible match by creating a duplicate — and the minimal conversion UI (Section 10) instructs the TC to request Admin/Manager assistance rather than exposing any further detail about the restricted match. A `clientId` that does not exist, a `clientId` that exists but shares no normalized contact channel with the Lead, and a `clientId` that exists and matches but that the actor is not authorized for (fails `canAccessClient`) must all produce the identical `CLIENT_LINK_NOT_AVAILABLE` response (Section 9) — indistinguishable from one another — so this endpoint can never be used as a record-existence oracle for an arbitrary Client id.

  **4. Field mapping.** A newly created Client receives exactly the Lead's `fullName`, `email`, `phone`, `normalizedEmail`, and `normalizedPhone`, copied as they stand on the Lead at conversion time. `Lead.notes` is never copied to `Client.notes`: Lead-stage internal notes and Client-stage internal notes remain distinct historical records, consistent with blueprint Section 5's Lead/Client separation. `Client.notes` and every optional Section 13.3 profile field (`address`, `nationality`, `dateOfBirth`, `emergencyContact`) are left `null` on creation — populating them is Client Management's own, later, not-yet-implemented editing capability, not this checkpoint's concern. Linking to an existing Client never overwrites any field on that Client — not `fullName`, not any contact field, not any profile field — linking is a pure association, never a merge or update. The original Lead record is preserved unchanged apart from its own status/`clientId` fields (blueprint Section 6.7's "preserved for historical and audit reference rather than deleted"); the link is recorded exclusively through the existing `Lead.clientId` foreign key.

  **5. Assignment behavior.** When conversion creates a new Client, that Client atomically inherits the Lead's current active assignee, if the Lead has one — reusing the existing, unchanged `features/assignments/repository.ts`'s `createAssignment` with `clientId` as the target, exactly as `createLead`'s existing Travel-Consultant-self-assignment-at-creation transaction already demonstrates the pattern (D-022 §2). The new Client assignment's `assignedByUserId` is the converting actor, regardless of whether the inherited `assignedStaffId` is that same actor or someone else (e.g., an Admin/Manager converting a Lead assigned to a Travel Consultant). If the Lead has no active assignment at conversion time (an Admin-created, never-assigned Lead, D-022 §2), the new Client is created with no assignment — conversion never invents one. Linking to an existing Client never creates, ends, or otherwise changes that Client's assignment in any way, regardless of whether it matches, differs from, or is entirely independent of the Lead's own assignee — an existing Client's assignment state is never a side effect of any Lead being linked to it. Reassigning a Client — whether one just created by conversion or one linked to it — remains exclusively a separate, subsequent `ADMIN_MANAGER` action through the existing, unchanged `PUT /api/clients/[id]/assignment` endpoint; this checkpoint does not add, change, or bypass that endpoint.

  **6. Transaction, history, and side effects.** Conversion executes inside the existing `runSerializableWithRetry` (`@/lib/serializable-transaction`), exactly as `updateLeadStatus` and `updateBookingStatus` already do. Within that one serializable transaction, in order: (a) reload the Lead; (b) for a `TRAVEL_CONSULTANT` actor, revalidate their active assignment for this Lead using the existing, unchanged, transaction-aware `assignmentRepository.findActiveAssignmentForLead(tx, leadId)` (`features/assignments/repository.ts`) — a transaction-local recheck of the identical policy the pre-transaction `canAccessLead` check (Section 2) already expressed, not a new or different authorization rule; an `ADMIN_MANAGER` actor remains unconditionally authorized once Lead existence is confirmed, with no further recheck required. A failed recheck here (the TC's assignment ended or changed between the initial check and this point) produces the same `LEAD_FORBIDDEN` outcome the initial check would have produced. (c) enforce eligibility (current status is `QUALIFIED`) and the `expectedStatus` concurrency check (Section 7); (d) re-run Client duplicate matching and, for a supplied `clientId`, validate the link (Section 3), including — for a `TRAVEL_CONSULTANT` actor — revalidating `canAccessClient`'s identical policy via the existing, unchanged, transaction-aware `assignmentRepository.findActiveAssignmentForClient(tx, clientId)`; an `ADMIN_MANAGER` actor remains unconditionally authorized for any existing, matching Client. A failed recheck here produces the same `CLIENT_LINK_NOT_AVAILABLE` outcome Section 3 already defines for an unauthorized `clientId`. (e) create the new Client or resolve the existing one; (f) when creating a new Client and the Lead has an active assignee, create the inherited Client assignment (Section 5); (g) set `Lead.clientId` to the resulting Client's id; (h) set `Lead.status` to `CONVERTED_TO_CLIENT`; (i) insert the `LeadStatusHistory` row recording `previousStatus: QUALIFIED, newStatus: CONVERTED_TO_CLIENT`; (j) write every required `AuditLog` entry (Section 8). All of (a) through (j) commit or roll back together — a concurrent request can never observe a Lead marked `CONVERTED_TO_CLIENT` without its Client existing, linked, and audited, or a Client created without its Lead being updated. Both transaction-local rechecks in (b) and (d) exist because `canAccessLead`/`canAccessClient` run against the global Prisma client and cannot themselves be called inside `runSerializableWithRetry`'s transaction client, while `assignmentRepository.findActiveAssignmentForLead`/`findActiveAssignmentForClient` already accept a `Prisma.TransactionClient` as their first argument, exactly as every other in-transaction repository call in this codebase does — no change to `features/assignments/*` is required to support this. Duplicate matching and all authoritative link validation (Section 3) remain entirely inside this transaction, never performed only beforehand. Conversion must never create any downstream or portal record as a side effect: no portal invitation, User account, Proposal/ROS, Booking, Payment Plan, Visa Case, or notification, per blueprint Section 5.1 and consistent with blueprint Section 5.2's conceptual-relationship diagram, in which each of those remains its own later, separate, explicit staff action.

  **7. Concurrency and idempotency.** `expectedStatus` is required on every request and must be the literal value `"QUALIFIED"` at the schema level; the service layer additionally re-confirms the Lead's actual current status inside the transaction before proceeding, mirroring `updateLeadStatus`'s existing pattern (D-022 §7). The already-converted idempotency check runs before `expectedStatus` conflict handling, mirroring D-022 §6's same-status-no-op-runs-first precedent exactly. If the Lead is already `CONVERTED_TO_CLIENT`, the replay path reads — but never writes — the Lead's own `clientId` and the sanitized `LEAD_CONVERTED_TO_CLIENT` `AuditLog` entry Section 8 requires every conversion to write; that entry's `afterState` (`{ status, clientId, clientCreated }`) is the sole, explicitly designated persisted source of the `clientCreated` value a replay reports, since neither `Lead` nor `Client` itself records whether the original conversion created or linked the Client. A request with an omitted `clientId` returns the existing conversion result — the Lead's current `clientId` plus the audited `clientCreated` value — unchanged, with no new write of any kind. A request whose supplied `clientId` equals the Lead's existing `clientId` likewise returns that same audited result, with no new write. A request whose supplied `clientId` differs from the Lead's existing `clientId` returns `LEAD_CONFLICT` rather than silently accepting the second, differing choice or creating a second Client. If the Lead is `CONVERTED_TO_CLIENT` but its `LEAD_CONVERTED_TO_CLIENT` audit entry is missing, or that entry's `afterState.clientId` does not match `Lead.clientId`, the replay does not guess — it returns `LEAD_CONFLICT` rather than fabricating a `clientCreated` value from unreliable state. An idempotent success writes no new `LeadStatusHistory` row, no new `StaffAssignment` row, no new `Client` row, and no new `AuditLog` entry of any kind — it is a pure read of already-committed Lead and audit state. A stale, non-idempotent request — the Lead's actual current status is not `QUALIFIED` and the request does not match one of the idempotent-replay cases above — returns `LEAD_CONFLICT`, mirroring `updateLeadStatus`'s existing stale-`expectedStatus` handling exactly, whether that Lead was never `QUALIFIED` to begin with or moved away from `QUALIFIED` after the caller last observed it: this endpoint does not distinguish the two, the same way `updateLeadStatus`'s own `expectedStatus` mismatch check does not. `CONVERTED_TO_CLIENT` remains terminal exactly as D-022 §6 already established: every outgoing transition from it is rejected, and ordinary Lead-field editing remains locked (`LEAD_LOCKED`) exactly as `updateLead`'s existing `CONVERTED_TO_CLIENT` check already enforces — this decision changes none of that existing behavior.

  **8. Audit contract.** Two new sanitized `AuditLog` actions are introduced: `LEAD_CONVERTED_TO_CLIENT` (entity type `Lead`) and `CLIENT_CREATED` (entity type `Client`) — added to `features/leads/audit.ts`'s existing `LEAD_AUDIT_ACTIONS` allow-list style. When assignment is inherited (Section 5), the existing `ASSIGNMENT_AUDIT_ACTIONS.CLIENT_ASSIGNED` action (`'CLIENT_ASSIGNMENT_CREATED'`, `features/assignments/audit.ts`) is reused unchanged — a new, differently named action is not introduced for this event, mirroring how `LEAD_ASSIGNED` is already reused for a Lead's own creation-time self-assignment (D-022 §7; `features/leads/audit.ts`'s existing doc comment). All audit writes for a single conversion occur inside the same transaction as the mutation they record (Section 6), never as a separate, later write. `LEAD_CONVERTED_TO_CLIENT`'s snapshot is limited to `status` (`'CONVERTED_TO_CLIENT'`), `clientId`, and `clientCreated` (boolean) — never any Lead PII, mirroring `sanitizeLeadStatusSnapshot`'s existing allow-list discipline; this same `afterState` is also the sole persisted source Section 7's idempotent replay reads for `clientCreated`, since neither `Lead` nor `Client` itself records it. `CLIENT_CREATED`'s snapshot is limited to `sourceLeadId` and `hasEmail`/`hasPhone` boolean flags — never `fullName`, `email`, `phone`, or any other Client field, mirroring `sanitizeLeadCreatedSnapshot`'s existing allow-list discipline exactly. The reused `CLIENT_ASSIGNED` entry's metadata follows its own existing, unchanged allow-listed sanitizer (`sanitizeAssignmentSnapshot`) — this decision does not alter it. No audit snapshot introduced or reused by this checkpoint ever stores a name, email, phone, note, arbitrary request body, or any other profile data, consistent with `.claude/rules/database-security.md`'s Audit Records rule and D-022 §7's established precedent.

  **9. API and controlled errors.** The endpoint is `POST /api/leads/[id]/conversion`, guarded by `withRole(['ADMIN_MANAGER', 'TRAVEL_CONSULTANT'])` exactly like every other Lead mutation route. A successful response contains the updated Lead in the same mutation-style, assignment-free `LeadRecord` shape `updateLeadStatus` already returns (`features/leads/repository.ts`) — never `getLeadById`'s richer, GET-only `LeadRecordWithAssignment` shape, which D-023 §5's Stage 2 correction deliberately keeps exclusive to `findLeadByIdForRead`/`listLeadsForActor`; the assignment-enriched shape remains available only through the authorized `GET /api/leads/[id]` read the conversion UI's `router.refresh()` (Section 10) triggers afterward, not through this mutation's own response — plus a minimal Client summary limited to `id` and `fullName` only, and `clientCreated: boolean` indicating whether this specific request created the Client (`true`) or linked to an already-existing one (`false`) — an idempotent replay of an already-completed conversion (Section 7) reports `clientCreated` exactly as it was on the original, successful request. All error responses use the existing standard `{ error: { code, message, details? } }` envelope (`features/leads/http.ts`'s existing `validationErrorResponse`/`leadErrorResponse` conventions). Controlled error codes cover at minimum: `ROLE_NOT_PERMITTED` (403, service-layer defense-in-depth, mirroring `assertLeadActor`), `LEAD_NOT_FOUND` (404), `LEAD_FORBIDDEN` (403), `CONVERSION_NOT_ELIGIBLE` (409 — returned by the read-only conversion-options service of Section 10 when queried for a Lead that is not currently `QUALIFIED`, so the Lead-detail page and any direct caller of that read get a clear ineligibility signal distinct from a concurrency conflict), `CLIENT_MATCH_REQUIRES_LINK` (409, a matching Client exists but no `clientId` was supplied), `CLIENT_LINK_NOT_AVAILABLE` (409 — deliberately not 404, since a 404 would confirm non-existence and thereby distinguish the missing-`clientId` case from the unrelated/unauthorized cases, which Section 3 requires to remain indistinguishable), `LEAD_CONFLICT` (409, the mutation's own stale-`expectedStatus` or differing-`clientId` idempotency conflict — Section 7), and `VALIDATION_ERROR` (400, schema-boundary failures). These statuses are chosen for consistency with `features/leads/errors.ts`'s existing `LeadErrorCode`→status map (`LEAD_LOCKED`, `REASON_REQUIRED`, `INVALID_STATUS_TRANSITION`, `CONVERSION_ENDPOINT_REQUIRED`, and `LEAD_CONFLICT` are all already 409; `LEAD_NOT_FOUND` is 404; `LEAD_FORBIDDEN` and `ROLE_NOT_PERMITTED` are 403). No `reason` field is required or accepted by this endpoint: Lead-to-Client conversion is D-022 §6's already-approved monotonic forward transition from `QUALIFIED`, and D-022 §6 requires a mandatory reason only for reopening/corrective transitions and transitions into `DUPLICATE`/`SPAM` — conversion is neither.

  **10. Conversion-options read and UI.** A new, independently authorized application-service read (e.g., `getConversionOptions` in `features/leads/service.ts` or a co-located module) is added, re-running the same eligibility, authorization, and Client-matching logic as the mutation (Sections 2–3) in read-only form, and is called directly by the server-rendered `/admin/leads/[id]` page (`apps/web/src/app/admin/leads/[id]/page.tsx`) — never by a client component calling a server-only service. This checkpoint does not create a general Client search or Client Management API; the conversion-options read exists solely to power this one panel and returns only what Section 3 already authorizes exposing (accessible candidates' `id`/`fullName`/matched channels, plus a `restrictedMatchDetected` flag). The conversion panel — a new `_components/ConvertToClientPanel.tsx` alongside the existing `EditLeadForm`/`StatusTransitionPanel` — renders only when the Lead's current status is `QUALIFIED`; it does not render for any other status, including `CONVERTED_TO_CLIENT` (which continues to show the existing locked/no-transitions state D-023 already established). The default, pre-selected action is "create a new Client," available only when the conversion-options read reports no matching Client at all. When one or more authorized candidates exist, each is presented as an explicit, individually selectable link choice showing only `fullName` and its matched channel(s) — never any other field. When only restricted matches exist, the panel shows a generic message directing the Travel Consultant to request Admin/Manager assistance, with no further candidate detail, matching Section 3's restriction exactly. No free-text Client-id input control is offered anywhere in this UI — every selectable choice comes from the conversion-options read, never an arbitrary typed value (mirroring D-023 §7's existing "no optimistic invention of state" and the absence of any Client search surface, Section 10 above). The panel requires an explicit user confirmation step before submission (`.claude/rules/admin-dashboard.md`'s Destructive and Irreversible Actions rule — conversion is irreversible). The browser mutation calls `POST /api/leads/[id]/conversion` directly via `fetch`, parses the standard controlled error envelope exactly as `EditLeadForm`/`StatusTransitionPanel` already do, and calls `router.refresh()` after a successful response so the server-rendered Lead state is reconciled with the database — never optimistically assuming success. After that refresh, the existing converted/locked Lead state (D-023's already-implemented `initiallyLocked`/no-status-options behavior) becomes authoritative and the conversion panel itself no longer renders.

  **11. Testing contract.** Automated coverage is required at every existing tier: schema validation tests for the new request schema (empty body, wrong `expectedStatus` literal, malformed `clientId`, unknown extra properties rejected by `.strict()`); audit-sanitizer tests for `LEAD_CONVERTED_TO_CLIENT`'s and `CLIENT_CREATED`'s new sanitizers, confirming their allow-listed shape; mocked service unit tests; route tests for the new `POST /api/leads/[id]/conversion` handler; component tests for `ConvertToClientPanel`; and real-PostgreSQL integration tests extending `features/leads/service.integration.test.ts`. Coverage must include: both authorized roles and every prohibited role; `TRAVEL_CONSULTANT` active-assignment authorization, including the identical `LEAD_FORBIDDEN` response for an inaccessible versus a nonexistent Lead; both the create-new and link-existing paths; both an accessible and a restricted duplicate Client match; that creation of a new Client is blocked (`CLIENT_MATCH_REQUIRES_LINK`) whenever any Client match exists at all, not only when every match happens to be restricted; the Travel-Consultant-blocked-from-creating-when-only-restricted-matches-are-visible case specifically; that an unrelated, a missing, and an unauthorized supplied `clientId` all produce the identical, indistinguishable `CLIENT_LINK_NOT_AVAILABLE` outcome; the exact field mapping onto a newly created Client and the deliberate non-copying of `notes`; assignment inheritance when the Lead has an active assignee, and the no-assignment outcome when it does not; that linking to an existing Client never creates, ends, or changes that Client's assignment; that the Lead status/`clientId` update, `LeadStatusHistory` insert, Client creation, inherited-assignment creation, and every audit entry commit atomically together; idempotent retries (omitted `clientId`, matching `clientId`) after an already-completed conversion, including that a replay of a creation reports `clientCreated: true` and a replay of a link reports `clientCreated: false`, both read from the `LEAD_CONVERTED_TO_CLIENT` audit entry and never re-derived any other way; that a replay against a `CONVERTED_TO_CLIENT` Lead whose `LEAD_CONVERTED_TO_CLIENT` audit entry is missing, or whose `afterState.clientId` disagrees with `Lead.clientId`, returns `LEAD_CONFLICT` rather than a guessed result; a stale `expectedStatus` and a differing-`clientId` retry both producing `LEAD_CONFLICT`; and that no downstream record (portal invitation, User account, Proposal/ROS, Booking, Payment Plan, Visa Case, notification) is ever created by this checkpoint.

  **12. Constraints and effect.** No `schema.prisma` change and no migration are authorized or required by this decision. `Lead.clientId`, `Client`'s normalized contact fields (`normalizedEmail`/`normalizedPhone`), `LeadStatusHistory`, the Lead/Client `StaffAssignment` mechanisms (`StaffAssignment.clientId` and its existing partial-unique-active-assignment index), `Client.leads` (the Prisma-side reverse relation to `Lead.clientId`, not a separate migrated column), and the `CONVERTED_TO_CLIENT` `LeadStatus` value all originate from migration `20260714024613_lead_client_assignment_foundation` — the same migration D-022 §1 already confirmed as sufficient for Lead Management Core. `AuditLog` originates separately, from the earlier migration `20260713062622_staff_role_management_foundation`, not from the Lead/Client migration. All of the above are already migrated and already fully support every mechanism described in this decision; no new `schema.prisma` change or migration is authorized or required. This decision does not itself mark the Phase 2 "Explicit Lead-to-Client conversion" checklist item complete in `docs/HERITAGE_V3_TASK_BOARD.md`; that update remains a later, separate step, made only once the implementation and its required automated and real-PostgreSQL integration coverage (Section 11) actually exist and pass.

- **Rationale:** Reusing `runSerializableWithRetry`, `canAccessLead`/`canAccessClient`, the standard `{ error: { code, message } }` envelope, and allow-listed audit snapshots keeps conversion consistent with every already-reviewed Lead, Booking, and Assignment mutation rather than inventing a parallel mechanism. Blocking new-Client creation whenever any system-wide match exists, and shaping match visibility exactly like D-022 §5's existing duplicate-detection rule, prevents Section 6.7's "without duplicating it" guarantee from being silently violated at the one moment a permanent Client record is created, and keeps this checkpoint from becoming a new information-disclosure surface beyond what already-approved Lead editing exposes. Propagating assignment only on create-new, and never touching an existing Client's assignment on link, avoids conversion silently reassigning a Client that `/api/clients/[id]/assignment` already exclusively manages. Modeling idempotency on the already-established same-status-no-op (D-022 §6) and natural-key-create (Booking's `attemptCreateBooking`) precedents makes a lost-response retry safe without inventing a new concurrency primitive. Deferring Client management, portal invitation, User account creation, Proposal/ROS, Booking, Payment Plan, Visa Case, and notifications preserves blueprint Section 5.1's non-automatic-creation rule and avoids building ahead of their own, separate, not-yet-authorized checkpoints.
- **Constraint:** No `schema.prisma` or migration change is authorized or required. No existing API path, request shape, or authorization rule is renamed or altered — `PUT /api/leads/[id]/status` continues to return `CONVERSION_ENDPOINT_REQUIRED` for `QUALIFIED → CONVERTED_TO_CLIENT` exactly as D-022 §6 already established, and this new `POST /api/leads/[id]/conversion` endpoint is the "dedicated conversion workflow" that error message already refers to. `features/assignments/*` and its existing routes (`/api/leads/[id]/assignment`, `/api/clients/[id]/assignment`) are reused unchanged, not modified. This decision does not implement Client management, Proposal/ROS, Booking UI, or any later Phase 2 checkpoint, and does not resolve `Client.status` (D-021's open item (b), still open).
- **Deferred:** Client CRUD/management backend and UI; portal invitation; User account creation; Proposal/ROS; Booking; Payment Plan; Visa Case; any notification; a general Client search or browse capability beyond the narrowly scoped conversion-options read; general AuditLog/ActivityLog browsing; and all schema, migration, environment, deployment, and infrastructure work.
- **Effect:** Authorizes implementation of the Phase 2 "Explicit Lead-to-Client conversion" checklist item in `docs/HERITAGE_V3_TASK_BOARD.md`. Does not itself mark that item, or any other Task Board item, complete — that update remains a later, separate step once the implementation and its automated/integration coverage actually exist and pass. Does not implement Client management, Proposal/ROS, Booking UI, the admin-dashboard overview, or any other not-yet-implemented Phase 2 checkpoint, and does not itself write any application code, schema, or migration.

## D-025 — Client Management authorization, editing, assignment UI, and concurrency contract

- **Status:** Accepted
- **Date accepted:** July 30, 2026
- **Decision:** The Client Management checkpoint (blueprint Sections 4, 5, 13.3; D-006; D-009; D-021; D-022; D-023; D-024; `docs/HERITAGE_V3_TASK_BOARD.md` Phase 2's "Client management backend and UI" item) is approved as follows. This entry is self-contained — it is the authoritative contract for implementation, not a pointer to a separate report.

  **1. Scope.** This checkpoint authorizes: a dedicated `features/clients` module; a paginated, assignment-scoped Client list; a single-Client detail read; Client ordinary-field editing; `GET /api/clients`; `GET /api/clients/[id]`; `PATCH /api/clients/[id]`; the `/admin/clients` and `/admin/clients/[id]` pages and their editing UI; a Client-only interactive assignment-management UI built on the existing, unchanged assignment endpoint/service (`PUT`/`DELETE /api/clients/[id]/assignment`, `features/assignments/service.ts`); read-only originating-Lead traceability; and the required unit, route, real-PostgreSQL integration, page, and component coverage for all of the above. It explicitly does not authorize, and defers: direct Client creation outside Lead-to-Client conversion, and therefore no `POST /api/clients` or any admin "Create Client" workflow; Client deletion, and therefore no `DELETE /api/clients/[id]`; `Client.status`, any status migration, status filter, status badge, or status-lifecycle transition; a Lead assignment-management UI (the parallel gap `docs/HERITAGE_V3_TASK_BOARD.md`'s "Wire existing Lead/Client staff-assignment functionality... into actual Lead/Client management workflows" item leaves open on the Lead side); client-portal invitation/activation UI; Proposal, Booking, Payment, Document, VisaCase, and Conversation/support-history summaries or counts on the Client detail view; and any general, cross-feature Client search API for a future, unrelated feature to consume. Clients continue to be created only through the already-accepted D-024 Lead-to-Client conversion workflow (`features/leads/service.ts`'s `convertLead`) — this decision does not add, replace, or duplicate that creation path.

  **2. Role and operation matrix.** `ADMIN_MANAGER` may list all Clients, read any Client, edit any Client, view all originating Leads for any Client, and assign, reassign, and end Client assignments through the existing, unchanged assignment workflow. `TRAVEL_CONSULTANT` may list only Clients they actively hold an assignment for, may read and edit only an actively assigned Client, may view that Client's current assignment information read-only, may view only the originating Leads they can independently access under Lead-assignment authorization (`canAccessLead`), and may not assign, reassign, or end any Client assignment. `SYSTEM_ADMINISTRATOR`, `FINANCE_ACCOUNTING`, `VISA_DOCUMENTATION`, and `CLIENT` are excluded from this admin Client-management surface entirely — no route, service function, or UI page introduced by this decision authorizes any of these four roles. Enforcement is layered: `withRole(['ADMIN_MANAGER', 'TRAVEL_CONSULTANT'])` gates the three new Client routes (Section 9); the existing `/api/clients/[id]/assignment` `PUT`/`DELETE` routes remain `withRole(['ADMIN_MANAGER'])`-only and unchanged; a new service-layer `assertClientActor`, mirroring `features/leads/service.ts`'s existing `assertLeadActor` exactly, independently rejects every non-`ADMIN_MANAGER`/non-`TRAVEL_CONSULTANT` role with `ROLE_NOT_PERMITTED`; the list query composes the `TRAVEL_CONSULTANT` assignment filter directly into the repository's Prisma `where` clause, never by fetching every Client and filtering in application code; every id-scoped read and edit calls the existing, unchanged `canAccessClient` (`features/assignments/authorization.ts`) before proceeding; and every `TRAVEL_CONSULTANT` `PATCH` additionally rechecks the active Client assignment transaction-locally — at the start of the mutation transaction, before any authoritative Client state is read or acted upon and before any success or write is returned (Section 7) — using the existing, unchanged, transaction-aware `assignmentRepository.findActiveAssignmentForClient(tx, id)`. The id-scoped `canAccessClient` primitive is never called for the list operation itself — list-time scoping is a repository-level query filter only, exactly mirroring `leadAssignmentFilter`'s existing precedent, never a per-row authorization check. For originating Leads specifically: `ADMIN_MANAGER` sees every Lead linked to the Client via `Lead.clientId`; `TRAVEL_CONSULTANT` sees only the subset independently allowed by Lead-assignment scoping, applied inside the repository query that reads the Client's `leads` relation — never by fetching every linked Lead and filtering client-side — and a Lead excluded by that scoping is omitted silently, with no hidden identity, metadata, or count ever revealed to the requesting Travel Consultant.

  **3. Client list contract.** `GET /api/clients` accepts `search` (optional, trimmed, minimum 1, maximum 200 characters), `page` (coerced integer, minimum 1, default 1), and `pageSize` (coerced integer, minimum 1, maximum 100, default 20) — the identical shape and limits `features/leads/schemas.ts`'s `listLeadsQuerySchema` already establishes. A whitespace-only `search` value is invalid at the API-schema layer (trimming reduces it to an empty string, which then fails the schema's minimum-length check, producing `VALIDATION_ERROR`); the `/admin/clients` page's own server-rendered filter form may normalize a truly empty submitted `search` value to `undefined` before validation, mirroring `admin/leads/page.tsx`'s existing `normalizeBlankParam` precedent, so an untouched native form field does not itself trigger a validation error. No `Client.status` filter exists, consistent with Section 1's deferral, and no assignment filter beyond the mandatory Travel-Consultant scoping itself is introduced. `search` matches case-insensitively across `fullName`, `email`, and `phone` only. Results are ordered by `createdAt` descending, then `id` descending as a deterministic tie-breaker, matching every other paginated list in this codebase. The response is `{ items, page, pageSize, total }`. Each list item contains only `id`, `fullName`, `email`, `phone`, `createdAt`, and `assignment: { staffId: string, staffName: string } | null` — an unassigned Client's `assignment` key is always present, with value `null`, never omitted. A list item must never include `normalizedEmail`, `normalizedPhone`, `address`, `nationality`, `dateOfBirth`, `emergencyContact`, `notes`, `updatedAt`, originating-Lead data, or any audit information — the list is a summary projection only, deliberately narrower than the detail response in Section 4.

  **4. Client detail contract.** `GET /api/clients/[id]` returns `{ client }`, where `client` contains exactly the following keys — no more, no fewer: `id`, `fullName`, `email`, `phone`, `address`, `nationality`, `dateOfBirth`, `emergencyContact`, `notes`, `createdAt`, `updatedAt`, `assignment`, and `originatingLeads`. Every nullable profile field (`email`, `phone`, `address`, `nationality`, `dateOfBirth`, `emergencyContact`, `notes`) is always present in the response, with a value of `null` when unset — never an omitted key. `assignment` is always present as either `{ staffId: string, staffName: string }` or `null` (same always-present-key convention as Section 3), never omitted. `originatingLeads` is always present as an array — `[]` when the Client has no originating Lead — never omitted and never `null`. Each entry in `originatingLeads` contains only `id`, `fullName`, `status`, `source`, and `createdAt` — reading the existing `Client.leads` reverse relation (`schema.prisma`), scoped per Section 2's Lead-assignment visibility rule for a `TRAVEL_CONSULTANT` actor, and ordered `createdAt` descending then `id` descending. `normalizedEmail` and `normalizedPhone` are internal implementation fields and must never be returned by the Client list, detail, or `PATCH` response, under any role. `createdAt` and `updatedAt` are serialized as ISO-8601 UTC timestamps (standard `Date`-to-JSON serialization, unchanged from every other timestamp field already returned elsewhere in this codebase); `dateOfBirth` is serialized only as a bare `YYYY-MM-DD` date, never a timestamp, matching the underlying `@db.Date` column's date-only precision.

  **5. PATCH schema and field behavior.** `PATCH /api/clients/[id]`'s request body is `.strict()` (an unknown key is rejected) and requires `expectedUpdatedAt` plus at least one editable-field key; a body containing only `expectedUpdatedAt` is rejected as invalid, since no edit is being requested. The eight editable fields are `fullName`, `email`, `phone`, `address`, `nationality`, `dateOfBirth`, `emergencyContact`, and `notes`. `fullName`, when present, is a trimmed string of 1–200 characters and can never be `null` or cleared to blank — identical to `Lead.fullName`'s existing, deliberate restriction (`features/leads/schemas.ts`'s `fullNameSchema`, used untransformed on both the create and edit schemas). `email` is a trimmed string of at most 320 characters; a blank string clears it to `null`; this decision preserves the existing accepted Lead email-format behavior exactly (no format/regex validation beyond length — `features/leads/schemas.ts` imposes none either) and does not introduce a new, Client-only format rule. `phone` is a trimmed string of at most 50 characters; a blank string clears it to `null`; this decision likewise preserves the existing accepted Lead phone behavior exactly, with no additional format rule. `address` is a trimmed string of at most 500 characters, blank-clears to `null`. `nationality` is a trimmed string of at most 100 characters, blank-clears to `null`. `emergencyContact` is a trimmed string of at most 200 characters, blank-clears to `null`. `notes` is a trimmed string of at most 2,000 characters, blank-clears to `null` — the identical limit `features/leads/schemas.ts`'s `notesFieldSchema` already uses. `dateOfBirth` accepts a bare `YYYY-MM-DD` string that must denote a real Gregorian calendar date — the day-of-month must be valid for its stated month and year (e.g. `2024-02-29` is accepted as a genuine leap day, while `2025-02-29` and any day-of-month that does not exist, such as `2026-04-31`, are rejected outright, never silently rolled over or normalized to a nearby valid date) — or `null`/a blank string to explicitly clear it; an omitted `dateOfBirth` key preserves the Client's existing value; a supplied date is persisted explicitly as UTC midnight for the Prisma/PostgreSQL `@db.Date` column (`schema.prisma`'s `Client.dateOfBirth DateTime? @db.Date`) and is returned as `YYYY-MM-DD`; a date later than the current Philippine business date is rejected; no artificial lower bound is imposed on how far in the past it may fall. `expectedUpdatedAt` is required on every request, is a strict ISO-8601 UTC timestamp string with exactly three-digit millisecond precision (matching what `Date.prototype.toISOString()` always produces), is used only as a concurrency comparison token (Section 7), and is never persisted to the `Client` row or written to any `AuditLog` entry. Every editable field omitted from the request body retains its current stored value — Prisma's `update` skips any key whose value is `undefined`, and this schema relies on that convention unchanged. After combining the Client's existing `email`/`phone` with whatever the request supplies for those two keys, the resulting Client must retain at least one of `email` or `phone`; violating this returns `VALIDATION_ERROR` with the exact message "A client must retain at least one of email or phone." A request whose editable-field values, once combined with the existing record, are identical to the currently stored values is a permitted no-op: it may still succeed, but only after `expectedUpdatedAt` and authorization are both independently verified first — a no-op request carrying a stale `expectedUpdatedAt` still returns `CLIENT_CONFLICT`, never a silent success — and a genuine no-op success performs no `Client` row write and creates no `AuditLog` entry (Section 8).

  **6. Contact normalization and duplicate detection.** The exact `normalizeEmail`/`normalizePhone` algorithms D-022 §4 approved are preserved unchanged; their single authoritative implementation moves to `apps/web/src/lib/contact-normalization.ts`, with its test moved alongside it. Every existing import updates to the new path, including `features/leads/service.ts`'s static import and `features/leads/service.integration.test.ts`'s dynamic `import('./normalize')` (updated to the new path). `features/leads/normalize.ts` is removed outright once the move is complete — no re-export shim is retained, and neither algorithm is duplicated or behaviorally altered by the move. Repository ownership of duplicate-query primitives is unchanged and stays split: the existing Lead/conversion duplicate-query primitives (`findDuplicateLeadMatches`, `findDuplicateClientMatches`, `createClientFromLead`, `findClientSummaryById`) remain owned by `features/leads/repository.ts`, exactly as D-024 established; Client-edit duplicate queries — a new, self-excluding Client-vs-Client match query (excluding the Client's own id) and a new, self-excluding Client-vs-Lead match query (excluding any Lead whose `clientId` already equals the Client being edited, while still matching an unlinked Lead or a Lead linked to any other Client) — belong to `features/clients/repository.ts`, with each exclusion applied directly inside the repository query itself, never by fetching unfiltered results and excluding them afterward. This decision does not convert the D-024 conversion primitives into general Client-management primitives, and does not add a Client-scoped duplicate query to `features/leads`. During a Client `PATCH`, duplicate detection reruns whenever the `email` or `phone` key is supplied in the request, even when the resulting combined value is unchanged from the existing record — mirroring `features/leads/service.ts`'s `updateLead`'s identical `contactProvided` behavior exactly. The rerun normalizes the final combined contact values, checks other Clients (excluding the Client being edited via the new self-excluding query), and checks Leads other than the Client's own originating Lead(s) — excluding, via that same repository-level filter, any Lead whose `clientId` already equals the Client being edited, while still checking every unlinked Lead and every Lead linked to a different Client — reusing D-022's existing duplicate-reporting shape and visibility rules unchanged: an authorized match exposes only the existing allow-listed summary (`id`, `fullName`, matched channel(s), plus `status` for a Lead match); an inaccessible match collapses into `restrictedMatchDetected: true` with no identity, metadata, or count ever leaked; multiple matches remain an array, never auto-selected. Repository, service, and real-PostgreSQL integration coverage must prove that a Client's own originating Lead(s) are never returned as an accessible duplicate match and never collapsed into `restrictedMatchDetected`, while a genuinely unrelated Lead sharing a normalized email or phone with the Client is still reported normally under the existing visibility rules. Duplicate matches found during a Client `PATCH` are advisory and non-blocking — unlike D-024's conversion-time blocking behavior, an ordinary Client edit is never rejected because of a duplicate match, and duplicate detection therefore never produces its own error response during `PATCH`. This decision preserves D-024's existing rule that linking a Lead to an existing Client during conversion never overwrites any field on that Client — Client `PATCH` is a wholly separate, later, independently authorized action, and nothing in this decision alters D-024's conversion-time behavior in any way.

  **7. Optimistic concurrency and transaction behavior.** Every `PATCH` request requires `expectedUpdatedAt` (Section 5). The mutation runs inside a plain Prisma transaction (`prisma.$transaction(async (tx) => {...})`), mirroring `features/leads/service.ts`'s existing `updateLead` precedent for ordinary-field edits — not the `runSerializableWithRetry` helper `updateLeadStatus`/`convertLead` use for genuine multi-branch lifecycle-transition races, since no repository or implementation evidence shows a Client field edit needs that stronger isolation. Inside that transaction, in order: for a `TRAVEL_CONSULTANT` actor only, the active Client assignment is transaction-locally rechecked via the existing, unchanged `assignmentRepository.findActiveAssignmentForClient(tx, id)`, mirroring D-024 §6(b)'s identical transaction-local-recheck precedent — an `ADMIN_MANAGER` actor requires no such recheck, remaining unconditionally authorized once the Client's existence is confirmed; the authoritative current Client row is read, both to compute the combined-field invariant and duplicate-detection inputs (Sections 5–6) and to distinguish disappearance from staleness below; `expectedUpdatedAt` is verified against the persisted `updatedAt` even when the submitted editable-field values are unchanged (Section 5's no-op case); a genuine changed write is applied atomically by including both the Client's `id` and the expected `updatedAt` value in the update predicate (`updateMany({ where: { id, updatedAt: expectedUpdatedAt }, data })`), so the staleness comparison and the write itself are a single atomic database operation rather than a separate read-then-write pair; if that predicate matches no row, existence is re-checked inside the same transaction to distinguish a genuinely missing Client from a merely stale `expectedUpdatedAt`, preserving the same role-aware anti-enumeration split Section 9 defines rather than weakening it; on a successful write, the authoritative persisted Client row is re-read and returned; and the `CLIENT_UPDATED` audit entry (Section 8) is appended in the same transaction. The resulting outcomes are: a Client missing for an `ADMIN_MANAGER` actor returns `CLIENT_NOT_FOUND` (404, "Client not found."); a Client that is nonexistent or inaccessible for a `TRAVEL_CONSULTANT` actor returns `CLIENT_FORBIDDEN` (403, "You do not have access to this client.") — indistinguishable from one another, exactly mirroring `LeadError`'s established anti-enumeration convention; a `TRAVEL_CONSULTANT`'s assignment lost between the initial authorization check and the transaction-local recheck likewise returns `CLIENT_FORBIDDEN` (403, the same message); and an `expectedUpdatedAt` mismatch against a Client that does still exist and remains accessible returns `CLIENT_CONFLICT` (409, "This client has changed since it was last loaded. Refresh and try again."). `CLIENT_CONFLICT` never returns raw Client state or any other PII detail — code and message only, matching the established convention that only `VALIDATION_ERROR` ever carries a structured `details` array. On success, the `updatedAt` value on the returned, persisted Client becomes the UI's new concurrency baseline for its next `PATCH` request.

  **8. Audit contract.** A new `CLIENT_UPDATED` `AuditLog` action is added, using the existing, unchanged append-only `AuditLog` convention (`entityType: 'Client'`, `entityId`: the Client's `id`). Its closed snapshot contains only `changedFields` (field names only, in detection order), `hasEmail`, and `hasPhone` — mirroring `sanitizeLeadUpdateSnapshot`'s exact allow-listed shape and rationale (`features/leads/audit.ts`). `expectedUpdatedAt` is never audited, matching the established convention that a concurrency/transition token (e.g. Lead's `expectedStatus`) never appears in its own mutation's audit snapshot. Raw `fullName`, `email`, `phone`, `address`, `nationality`, `dateOfBirth`, `emergencyContact`, and `notes` values must never be written to `AuditLog`, in either `beforeState` or `afterState` — only field names and the two contact-presence flags. A no-op `PATCH` (Section 5) creates no `AuditLog` entry. The `CLIENT_UPDATED` audit insert and the Client row update occur inside the same transaction described in Section 7 — never as a separate, later write.

  **9. API and error contract.** This decision authorizes exactly three new routes: `GET /api/clients`, `GET /api/clients/[id]`, and `PATCH /api/clients/[id]`. No `POST` or `DELETE` Client resource route is authorized by this decision (Section 1). Every response uses the established `{ error: { code, message, details? } }` envelope. Controlled error codes and their HTTP status: `VALIDATION_ERROR` (400), `ROLE_NOT_PERMITTED` (403, reusing `LeadError`'s/`AssignmentError`'s existing wording and status for this identical service-layer defense-in-depth check), `CLIENT_FORBIDDEN` (403), `CLIENT_NOT_FOUND` (404), `CLIENT_CONFLICT` (409), and `INTERNAL_ERROR` (500, the existing generic unhandled-error mapping `withRole` already provides). Successful responses are: list — `200 { items, page, pageSize, total }` (Section 3); detail — `200 { client }`, `client` using Section 4's exact shape (Section 4); `PATCH` — exactly `200 { client, duplicateMatches?, restrictedMatchDetected? }`, where `client` uses Section 4's exact shape (with the fresh, post-write `updatedAt`). `duplicateMatches` (an array) and `restrictedMatchDetected` (a boolean) are present together, as a pair, only when the request supplied `email` or `phone`, exactly mirroring `UpdateLeadResult`'s existing `Partial<DuplicateMatchResult>` convention; when the request supplied neither `email` nor `phone`, both keys are omitted from the response entirely — never present as `null` or an empty placeholder. The existing `PUT /api/clients/[id]/assignment` and `DELETE /api/clients/[id]/assignment` routes are unchanged by this decision — same authorization, same request/response shape, same error codes.

  **10. This decision does not implement the parallel, still-missing Lead assignment-management UI (Section 1). The generic `Pagination` component moves from `apps/web/src/app/admin/leads/_components/Pagination.tsx` to `apps/web/src/app/admin/_components/Pagination.tsx`, with its test moved alongside it; the existing Lead pages' imports are updated to the new path; both the Lead and the new Client pages use this one relocated implementation — no second `Pagination` implementation is created.

  **11. This checkpoint authorizes Section 9.1's externally-recorded-response mechanism (Accept, Decline, or Request Changes, entered by staff on the client's behalf) as part of this same checkpoint, not as a separate follow-up: the record captures the response type, the client's stated response timestamp, the acting staff account, the response method (e.g., phone, email, in person), and a supporting evidence reference, exactly as `ProposalAcceptance`'s already-migrated external-attribution path requires. Portal-based (client-authenticated) responses remain deferred to Phase 3, when the client portal and `ClientProfile`-based session attribution actually exist; `ProposalAcceptance.respondingClientProfileId`/`respondingSessionIdAtResponse` remain schema-only until then. `DECLINE` and `REQUEST_CHANGES` are immutable historical responses recorded against the specific `ProposalVersion` they answer — neither terminates the Proposal, sets any Proposal-level status, nor prevents a Travel Consultant from creating and publishing a later revision regardless of an earlier version's response. A later revision may also supersede a version that was itself accepted (per blueprint Section 9's own "any subsequent change requires a new revision to be created and, if needed, re-accepted" text), without altering, unlinking, or otherwise affecting any `Booking` already created from that specific accepted historical `ProposalVersion` — `Booking.proposalVersionId`'s existing `onDelete: Restrict` foreign key to that exact version row is untouched by any later Proposal-level supersession. Exactly one `ProposalVersion` may receive at most one response, ever — enforced by `ProposalAcceptance.proposalVersionId`'s existing `@unique` constraint, not merely a service-layer policy; Section 7 below defines the resulting non-idempotent behavior.

  **5. Publish concurrency contract.** Every `POST /api/proposals/versions/[id]/publish` request supplies a required key, `expectedCurrentVersionId: string (uuid) | null` — the current client-visible version the actor observed for this Proposal before deciding to publish, or explicitly `null` when the actor observed no current version at all. This key is never optional or omittable, avoiding the omitted-versus-null ambiguity D-025 Section 3 already disambiguated for an analogous case. Inside one `runSerializableWithRetry` transaction, in this exact order: (a) the target `ProposalVersion` is fetched, scoped to what the actor may see; since publish is Travel-Consultant-only (Section 3 — this route is `withRole(['TRAVEL_CONSULTANT'])`, and `ADMIN_MANAGER` never reaches it), a nonexistent target and a target that exists but belongs to a Client the actor holds no active assignment for are indistinguishable and both produce the identical `PROPOSAL_VERSION_FORBIDDEN` (403) — never `PROPOSAL_VERSION_NOT_FOUND` (404) — consistent with the established anti-enumeration rule this codebase already applies wherever a lookup is scoped to a single non-administrative role; (b) the `TRAVEL_CONSULTANT` transaction-local active-assignment recheck (Section 3) runs; (c) if the target is already the current client-visible version (`clientVisibleAt IS NOT NULL AND supersededAt IS NULL`), this is a pure idempotent no-op — the version is returned unchanged, with no additional write and no new audit entry, checked before any other comparison below, mirroring `setLeadAssignment`'s/`setClientAssignment`'s own identical same-outcome-runs-first precedent; (d) if the target is already superseded (`supersededAt IS NOT NULL`), the request is rejected with `PROPOSAL_VERSION_SUPERSEDED` (409) — a superseded version can never be resurrected as current by a later publish call; (e) otherwise, the Proposal's authoritative current version (if any) is read inside the transaction and its id (or `null`, if none exists) is compared against the request's `expectedCurrentVersionId`; a mismatch returns `PROPOSAL_CONFLICT` (409, "The current version has changed since you last loaded this proposal. Refresh and try again.") rather than silently superseding a version the actor never observed; (f) on a match, the prior current version (if one exists) has its `supersededAt` set, the target version's `clientVisibleAt` is set, and the `PROPOSAL_VERSION_PUBLISHED` audit entry is written — all atomically, in the same transaction. The existing partial unique index `proposal_version_current_client_visible_key` (already migrated by the Proposal / ROS Schema Foundation checkpoint) remains the final database-level backstop if two publish requests somehow both pass step (e) concurrently; any residual conflict this backstop raises, and any residual SERIALIZABLE conflict (P2034) that survives `runSerializableWithRetry`'s own retry bound, is caught and translated to the identical controlled `PROPOSAL_CONFLICT` (409) response — never exposed to the route layer as a raw Prisma/PostgreSQL error, mirroring `features/bookings/service.ts`'s `isOtherKnownConflict` handling exactly.

  **6. Revision allocation, replay, and creation idempotency; API route table.** The next `versionNumber` for a new revision is computed as `MAX(versionNumber) + 1` for the Proposal, read inside the same `runSerializableWithRetry` transaction as the write, relying on SERIALIZABLE isolation to prevent two concurrent transactions from computing and committing the same next number. As a defense-in-depth backstop mirroring `features/bookings/service.ts`'s `createBooking`'s own `bookingReference`-collision retry loop exactly, a residual unique-constraint conflict on `ProposalVersion`'s existing `@@unique([proposalId, versionNumber])` index is caught by an outer bounded retry loop — up to three attempts — that opens a fresh transaction and recomputes `MAX(versionNumber) + 1` again, never leaking a raw Prisma/PostgreSQL error to the route layer and never silently overwriting an existing version. Creating a Proposal (with its first version) and creating a revision are both **not** idempotent: the schema deliberately permits multiple Proposals per Client and multiple coexisting unpublished drafts per Proposal, so neither operation has a natural key to replay against — every successful request creates exactly one new row, matching this codebase's existing Lead-creation precedent (duplicate detection flags a match for staff review; it never blocks, merges, or dedupes the write itself). A caller is responsible for not double-submitting either request, the same as every other create endpoint in this codebase. This checkpoint authorizes exactly five route-handler files, exposing exactly six HTTP endpoints between them (`/api/proposals/route.ts` alone exposes both `POST` and `GET`): `POST /api/proposals` (`{ clientId: uuid, content: string }` → `201 { proposal, version }`); `GET /api/proposals` (paginated, actor-scoped list → `200 { items, page, pageSize, total }`); `GET /api/proposals/[id]` (→ `200 { proposal, versions }`, each version including `content`, `clientVisibleAt`, `supersededAt`, `createdByUserId`, `createdAt`, and its `acceptance` if any); `POST /api/proposals/[id]/versions` (`{ content: string }` → `201 { version }`); `POST /api/proposals/versions/[id]/publish` (`{ expectedCurrentVersionId: uuid | null }` → `200 { version }`); and `POST /api/proposals/versions/[id]/response` (`{ responseType: 'ACCEPT'|'DECLINE'|'REQUEST_CHANGES', respondedAt: ISO-8601 string, responseMethod: string (trimmed, 1–100 characters), evidenceReference: string (trimmed, 1–500 characters) }` → `200 { acceptance }`). Every request body is `.strict()` — an unrecognized key fails validation with `VALIDATION_ERROR` (400) rather than being silently stripped, matching `createBookingSchema`'s established discipline. The full controlled-error-code-to-status map is: `ROLE_NOT_PERMITTED` 403; `CLIENT_NOT_FOUND` 404 / `CLIENT_FORBIDDEN` 403 (via `canAccessClient`); `PROPOSAL_NOT_FOUND` 404 / `PROPOSAL_FORBIDDEN` 403; `PROPOSAL_VERSION_NOT_FOUND` 404 / `PROPOSAL_VERSION_FORBIDDEN` 403; `PROPOSAL_VERSION_SUPERSEDED` 409; `PROPOSAL_VERSION_NOT_CURRENT` 409; `PROPOSAL_RESPONSE_ALREADY_RECORDED` 409; `PROPOSAL_CONFLICT` 409; `VALIDATION_ERROR` 400.

  **7. External-response recording — one-time, non-idempotent.** Recording a Section 9.1 external response is not idempotent. Because `ProposalAcceptance.proposalVersionId` is `@unique`, at most one response may ever exist for a given `ProposalVersion`. Inside the transaction, immediately after the identical view/response-recording authorization (Section 3) and the transaction-local `TRAVEL_CONSULTANT` recheck, the checks run in this exact, fixed order: first, whether a `ProposalAcceptance` already exists for this version — if one does, the request is rejected with `PROPOSAL_RESPONSE_ALREADY_RECORDED` (409) unconditionally, regardless of whether the newly submitted `responseType`, `respondedAt`, `responseMethod`, or `evidenceReference` match the existing row or differ from it, and **regardless of whether this version has since been superseded** — an already-responded version's response is immutable history and is never re-evaluated against the version's current lifecycle state; no fuzzy or partial-match replay is performed. Only when no `ProposalAcceptance` exists yet for this version does the request proceed to the second check: whether the target is the Proposal's current client-visible version at write time; if it is not, the request is rejected with `PROPOSAL_VERSION_NOT_CURRENT` (409). This ordering — existing-response check before current-version check — ensures a version that already carries a recorded response, even one long since superseded by a later revision, always reports `PROPOSAL_RESPONSE_ALREADY_RECORDED` rather than the misleading `PROPOSAL_VERSION_NOT_CURRENT`. Whether an earlier recording attempt actually succeeded is answered by reading the Proposal/version detail (`GET /api/proposals/[id]`), never by retrying the `POST`. On `ACCEPT` specifically, this same write is simultaneously the version's lock — derived per Section 4, with no separate stored flag.

  **8. UI scope and entry points.** The sole entry point for creating the first Proposal for a Client is a new `CreateProposalPanel` component rendered on the existing `/admin/clients/[id]` detail page — reusing that page's own already-established authorization context (`canAccessClient` already gates the page; a `TRAVEL_CONSULTANT` can only ever be viewing a Client they are assigned to) so that no new Client-search or Client-picker mechanism is introduced anywhere by this decision. Creating a revision of an existing Proposal is a distinct capability that belongs on `/admin/proposals/[id]`, not on the Client detail page: no `CreateProposalRevisionPanel` or equivalent component is added under `apps/web/src/app/admin/clients/[id]/_components/`. `/admin/proposals` provides a paginated, actor-scoped Proposal list; `/admin/proposals/[id]` provides the Proposal's full detail, complete version history, the revision-creation form, the publish action, and the Section 9.1 response-recording form — all four of these workflows live on this one detail page. `apps/web/src/app/admin/layout.tsx` gains a role-gated "Proposals" navigation link, visible to the same `['ADMIN_MANAGER', 'TRAVEL_CONSULTANT']` role set already used for the existing "Clients" link. No Proposal title or reference field is introduced anywhere by this decision: the blueprint never names one for Proposal (unlike Booking's explicit `bookingReference`, blueprint Section 13.4), and multiple Proposals belonging to the same Client are distinguished in every list or detail view using only the linked Client's identity, `Proposal.createdAt`, and each version's own existing identifiers and derived state — never an invented label. A legacy `ProposalVersion` row whose `content` is `NULL` (Section 1) remains fully readable through every list/detail/history view and displays an explicit "Content unavailable" state in place of the missing text, rather than an empty space, a rendering error, or a fabricated placeholder. Every rendering of a `ProposalVersion`'s lifecycle state (draft / current client-visible / superseded) and its response state (no response / Accept / Decline / Request Changes), where both apply to the same version, presents the two as separate, clearly labeled indicators rather than collapsing them into one combined label — so that a state such as "accepted, and later superseded by a newer version" remains unambiguous to the viewing staff member.

  **9. Audit contract.** Four new `AuditLog` actions are added: `PROPOSAL_CREATED`, `PROPOSAL_VERSION_CREATED`, `PROPOSAL_VERSION_PUBLISHED`, and `PROPOSAL_RESPONSE_RECORDED` — entity type `Proposal` for the first, `ProposalVersion` for the middle two, and `ProposalVersion` again for the last (identifying the version the response was recorded against). Every sanitizer is an explicit allow-list, matching `sanitizeBookingSnapshot`'s/`sanitizeAssignmentSnapshot`'s established convention, and never includes a `ProposalVersion`'s `content` field, in either `beforeState` or `afterState`, under any circumstance — an audit snapshot records only ids, version numbers, and lifecycle/response state transitions, never the authored business content. `evidenceReference` (Section 9.1) remains, at the schema and API layer alike, a bounded pointer or identifier only — never a full copy of correspondence, unrelated personal information, or an identity document — consistent with blueprint Section 9.1's own text and `.claude/rules/database-security.md`'s data-minimization principle; this checkpoint does not relax that limit anywhere, including inside audit snapshots.

  **10.   **3. F-01 — Medium implementation defect: incomplete transaction-local assignment-recheck protection in `updateLead`, `updateLeadStatus`, and `updateClient`.** Affects `LEAD-04`, `LEAD-05`, and `CLIENT-03`. The discovery pass found that the assignment-based authorization check performed for a `TRAVEL_CONSULTANT` actor, and the protected business mutation it is meant to gate, are not guaranteed today to operate against one consistent, serializable transactional view of the target's `StaffAssignment` state. Concretely: `updateLead` (`features/leads/service.ts`) and `updateClient` (`features/clients/service.ts`) each run their write inside a plain `prisma.$transaction`, whose isolation level is whatever the connected PostgreSQL database happens to be configured with rather than an isolation level this codebase's application layer itself enforces; `updateLead` and `updateLeadStatus` (`features/leads/service.ts`) perform no transaction-local recheck of the acting consultant's Lead assignment at all — `updateLeadStatus` rechecks only `Lead.status`/`expectedStatus`, never the assignment; `updateClient` already performs a transaction-local recheck of the Client assignment, and that recheck is real-database proven to close the race window between the pre-transaction authorization check and the moment the recheck itself executes, but is not proven — and, under its current plain-transaction mechanism, is not actually closed — against a second race window in which the assignment changes after that recheck succeeds but before the mutation's business write commits.

  Stage 2 implementation must, for all three functions:
  - Use the repository's existing `runSerializableWithRetry` mechanism (`apps/web/src/lib/serializable-transaction.ts`) as the transaction wrapper. `updateLeadStatus` already uses this mechanism and requires no isolation-level change. `updateLead` and `updateClient` must each be converted from their current plain `prisma.$transaction` to `runSerializableWithRetry`.
  - Perform the applicable assignment-authorization recheck — `assignmentRepository.findActiveAssignmentForLead(tx, id)` for `updateLead`/`updateLeadStatus`, `assignmentRepository.findActiveAssignmentForClient(tx, id)` for `updateClient` (both already-existing, already-used-elsewhere repository functions, already accepting a `Prisma.TransactionClient`) — for a `TRAVEL_CONSULTANT` actor only, as the first operation inside the transaction, keeping the recheck strictly transaction-local. `updateClient`'s existing recheck is retained, not replaced, and now runs under the stronger isolation level.
  - Preserve every existing role and assignment policy this discovery verified elsewhere in the codebase without alteration — `ADMIN_MANAGER` continues to require no recheck of any kind, remaining unconditionally authorized once the target's existence is confirmed.
  - Prevent an assignment change occurring during the mutation from allowing a now-stale authorization decision to protect a write that should no longer be permitted.

  **Required error behavior**, distinguishing two outcome paths precisely:
  - A retry attempt whose own transaction-local recheck observes that the acting consultant's assignment access has been lost or changed must return the existing controlled `LEAD_FORBIDDEN` (Lead) or `CLIENT_FORBIDDEN` (Client) result — both already-defined, already-used error codes, no new code introduced. That controlled forbidden result is a plain application error, not a Prisma-coded conflict, and must not itself be retried by `runSerializableWithRetry`'s retry logic.
  - If a retryable `P2034` serialization conflict recurs on every one of `runSerializableWithRetry`'s bounded attempts, the exhausted conflict must be mapped to the existing controlled `LEAD_CONFLICT` (Lead) or `CLIENT_CONFLICT` (Client) result — again, both already-defined, already-used codes reused for this new code path, never invented. This exhaustion outcome must never be represented as `LEAD_FORBIDDEN`/`CLIENT_FORBIDDEN` (an exhausted, ambiguous retry sequence never actually confirms the specific denial a forbidden result asserts), and no raw Prisma or PostgreSQL error of any kind may escape to the route layer or caller.
  - Neither outcome path may produce an `AuditLog` row for the rejected business mutation. A concurrent `ADMIN_MANAGER` reassignment that legitimately triggers this race by committing during it separately, correctly writes its own `LEAD_ASSIGNMENT_CREATED`/`LEAD_ASSIGNMENT_REPLACED`/`CLIENT_ASSIGNMENT_CREATED`/`CLIENT_ASSIGNMENT_REPLACED`-family audit entry (already covered by D-030) for that successful, separate mutation; this legitimate audit entry must never be read, in any test or in any implementation reasoning, as evidence of an audit entry for the rejected, unauthorized business mutation, which correctly produces none.

  **Mechanism note, required to keep the tests below executable.** `runSerializableWithRetry` (`apps/web/src/lib/serializable-transaction.ts`) re-invokes its entire callback — including the transaction-local recheck — fresh, inside a brand-new transaction, on every one of its bounded attempts (three total: an initial attempt plus up to two retries), and retries only a Prisma-coded `P2034` conflict; any other thrown error, including a domain error such as `LEAD_FORBIDDEN`, propagates immediately and ends the attempt loop (confirmed directly against this file's own implementation and its existing test suite, `lib/serializable-transaction.test.ts`). Consequently, a single real, concurrently-committing `ADMIN_MANAGER` reassignment does not, and cannot be relied on to, deterministically exhaust all bounded attempts: it can cause `P2034` on at most the one attempt genuinely racing against it, and the very next attempt's own fresh transaction-local recheck then observes the reassignment's already-committed effect and correctly throws the controlled forbidden result — which is a plain domain error, not a `P2034`, and is therefore not retried further. Genuine bounded-retry exhaustion (every attempt independently receiving `P2034`) is not an outcome one committed concurrent reassignment can be relied on to produce, and this decision does not require or claim otherwise.

  **Required tests, for each of `updateLead`, `updateLeadStatus`, and `updateClient` individually** (a shared test helper may be used only if each resulting case remains individually attributable to its specific function):
  1. **Assignment loss followed by a successful retry**, proven at two tiers: (i) a deterministic mocked unit test in which the first simulated transaction attempt receives a `P2034`-shaped conflict and the second attempt's mocked transaction-local recheck reports the assignment lost or reassigned, asserting the function returns the controlled forbidden result and that this result is not itself retried; and (ii) a genuine real-PostgreSQL concurrency test against `heritage_v3_test` that (a) begins the assignment-scoped mutation as a real, in-flight transaction; (b) allows its transaction-local assignment recheck to execute and succeed; (c) deterministically pauses the mutation after that recheck but before its business write or commit; (d) runs and commits exactly one real, concurrent `ADMIN_MANAGER` reassignment against the same target; and (e) resumes the paused mutation and asserts it resolves to the controlled forbidden result via PostgreSQL's own serialization-conflict detection and `runSerializableWithRetry`'s retry — never a silent success and never a raw database error.
  2. **Genuine bounded-retry exhaustion**, proven by a deterministic mocked unit test only, mirroring this codebase's own already-established precedent for the identical mechanism (`features/leads/service.test.ts`'s existing `convertLead` test "maps a serialization conflict that survives every retry to `LEAD_CONFLICT`, never a raw Prisma error," and `lib/serializable-transaction.test.ts`'s own "gives up and rethrows the raw error after exhausting retries on repeated conflicts" test): the underlying transaction call is stubbed to reject with a `P2034`-shaped error on every one of `runSerializableWithRetry`'s bounded attempts, deterministically, independent of any real database state, and the test asserts the function maps the exhausted conflict to the existing controlled `LEAD_CONFLICT`/`CLIENT_CONFLICT` result — never a forbidden result, and never a raw `PrismaClientKnownRequestError` reaching the route layer. This decision does not require a real-PostgreSQL bounded-exhaustion test: per the mechanism note above, the single, concurrently-committing `ADMIN_MANAGER` reassignment authorized for item 1's real-PostgreSQL sequence cannot by itself prove bounded exhaustion, since it resolves on the very next attempt's fresh recheck rather than recurring on every attempt — so, under this contract, bounded exhaustion is proven deterministically at the mocked-unit tier only, while genuine real-PostgreSQL coverage remains required for the single-conflict-then-fresh-retry-to-forbidden path (item 1). This is not a claim that every conceivable real-PostgreSQL test harness is incapable of producing a conflict on every bounded attempt — only that the single-reassignment sequence this decision authorizes cannot, and this decision neither requires nor authorizes a more elaborate real-database orchestration to attempt it.
  3. Confirmation that the mutation's business write never appears in final persisted state when the mutation is rejected under either outcome in items 1–2 above, and that no audit row is written for the rejected attempt (Section 3, "Required error behavior," third bullet).
